### 1.2 技术架构

```
SwiftUI（界面、用户交互、平台服务适配）
    ↓ AppBackend / 同步 FFI
panda-ffi（简单值类型；异步工作使用既有全局 tokio runtime）
    ↓
panda-core（配置、分组、凭据逻辑、SSH、SFTP、主机密钥、遥测）
```

业务规则位于 Rust 核心；平台调度可用性、文件访问与系统服务由适配层提供。共享核心不意味着所有平台拥有相同的运行条件。

## 二、AI 时代关键判断

> #14：以下为产品假设和工程判断，不把市场趋势当作需求验证。

### 判断 1：优先验证远程任务中的人工投入与出错点

[假设] Panda SSH 的 AI 价值在于减少远程巡检与排障的资料搜集、重复输入、结果比对和人工修正。是否需要意图入口、自动摘要或长期记忆，应由具体任务表现决定。

[已核对] Warp 客户端已开源并支持远程 SSH Agent。不能再以「竞品仅本地、闭源、只有补全」证明市场空白；详见 8.2、14.1。

[建议] 首个验证场景为小规模服务器的人工触发巡检与故障初筛。目标角色、实际主机规模、远端系统与现有工作方式须在首个提案中确认，不从场景列表数量推导优先级。

### 判断 2：AI 提供建议，授权与执行边界由确定性代码维护

- 学习、记忆、模型输出和 Skill 文本不能创建或扩大授权，也不能更改审批状态或审计记录。
- 本地推理减少云端传输，但不自动保证数据安全；远端输出、模型、脚本与插件仍各有信任边界。
- 云端调用、向外部 MCP 客户端返回数据，均需有明确的数据范围与接收方授权；执行授权不能替代数据外传授权。
- macOS 定时巡检仅复用人工审核且成功验证的执行计划，准入与失效规则见第四、十三章。iPadOS 不支持定时任务。

### 判断 3：差异化与 AI 增益必须用任务结果验证

[假设] 受控执行、清楚的证据展示和可发现缺段的本地审计，有机会形成可用的工作流优势；开源或接入 MCP 本身不足以证明这一优势。

验证时比较同一组任务的人工流程、固定规则/模板流程与 AI 辅助流程，衡量人工投入、修正负担、完成质量和错误操作。未证明增益时保留可用的非 AI 流程，暂缓增加基础设施。有限评测只能提供边界内证据，不能证明所有场景绝对安全；具体关卡见 8.5。

## 四、安全边界与约束原则

> #14 当前约束。历史记录中的「绝不自动执行」与「可信 Skill/命令模式可自动执行」均由本章的有效授权模型取代。本章约束产品设计，不授权当前 AI 合作者执行远程操作。

### 4.1 权限与信任边界

| 原则 | 必须满足的边界 |
|------|----------------|
| 有效授权是执行前提 | 所有系统代发远程操作均须落在有效授权范围内；手动终端输入本身是该次操作指令，不因审计新增逐键审批 |
| 学习系统不得扩权 | AI、记忆、反馈、Skill、工具描述及远端输出不能签发授权、扩大目标/参数/工具/时间范围、降低确认要求或修改审批状态 |
| Rust 执行入口统一强制检查 | UI、FFI、MCP、批量任务、定时器使用同一授权与执行约束；UI 展示或模型自律不能替代执行前检查 |
| 凭据隔离 | AI/MCP 仅获取完成任务所需的非敏感引用或结果，不获得凭据读取能力；连接层按授权使用凭据。当前存储基线冲突见 1.3，须先统一，不能虚称已经只存钥匙串 |
| 数据外传单独授权 | 终端内容、文件、报告、审计和派生记忆均不默认外传；明确数据范围、接收方/provider 与用途。混合模型不得静默切云端 |
| 不可信内容不能成为权限来源 | 日志、终端输出、检索内容、Skill 正文、MCP 工具注解只提供数据或候选建议；工具与本地文件访问按调用者隔离 |
| 平台边界明确 | 定时任务仅支持 macOS；iPadOS 不支持前台定时、后台定时或补跑，不通过服务器中转执行 |
| 开源与最小复杂度 | MCP/Skills 核心保持开源；可由确定性规则解决的问题先用规则，社区内容需独立审查来源、权限及许可 |

### 4.2 审批对象与有效期

审批对象是具体执行计划及其确定的范围，不是一个抽象 Skill 名称或宽泛命令模式。计划至少明确目标主机集合、身份、跳板链、命令和展开参数、工具/脚本/片段版本或内容标识、必要环境前提、验证步骤、资源预算与数据流向。

计划生成、用户审核、执行前检查必须针对同一版本。目标集合变化、内容更新、身份或跳板路径变化、授权撤销/过期、主机密钥异常，均不得继续复用旧授权。相同命令字符串不能掩盖其引用脚本已改变。如何冻结引用、处理确实需要变化的参数与执行前变化检查，在提案中设计；无法确认仍在授权范围内时停止。

一次性批准仅覆盖该次计划。定时巡检的周期授权只适用于第十三章规定的准入流程，不推广为任意可信命令模式自动执行。用户可暂停或撤销；撤销后不得新发起步骤，已发出操作的停止结果须如实记录。

### 4.3 macOS 定时巡检的准入

顺序固定为：生成具体计划 → 首次人工审核 → 人工触发执行 → 结果验证无问题 → 用户将该已验证计划加入定时任务。

没有成功验证记录、只有模型自评或仅有零退出码，都不满足准入。后续调度使用同一已授权计划，并逐次验证授权、前置条件和结果；不由 AI 在触发时改写计划。需要改变执行范围或内容时，重新经过审核、试跑和定时启用流程。

### 4.4 命令历史作为本地审计记录

[已决] 本地保留的命令执行历史是审计记录，必须关联实际操作、执行主体、有效授权、时间、目标、结果与验证证据；被拒绝、取消、失败或结果未知的尝试也需有可区分记录。

[已决] 删除记录后，系统必须能够清楚显示中间缺失了一段内容，不能把剩余历史静默呈现为完整历史。合法清理也需要保留可识别的清理/缺段信息；读取、验证和展示不能绕过完整性检查。学习系统不得改写历史、隐藏缺段或将推断替换为原始证据。

审计写入失败、存储耗尽或完整性无法核验时，不得静默继续系统代发任务。阻断新步骤、提示用户、保留已发出操作的未知状态及恢复记录的具体机制，在审计/执行提案中一并设计。

审计、终端录像、运行日志和 AI 记忆的用途不同。逐键输入不保证等于完整命令；只录输出也可能包含敏感内容。明确记录覆盖范围与置信度，秘密不得进入通用审计负载。脱敏或隐藏内容必须明确标记，不伪装成未发生操作或完整原文。

**存储方式、格式、连续性校验、删除留痕和密钥管理留待审计专项提案设计，不在脑暴阶段固定为某种数据库或哈希链。** 提案必须覆盖中间删除、尾部截断、重排、篡改、合法清理、写入中断与备份恢复等情形。

[边界] 仅依赖可被同一操作者全部替换的本地材料，无法无条件证明整库删除或完整旧副本回滚一定可检出。提案须定义可信边界及证据丢失时的「完整性无法验证」状态；不能以此取消已决的缺段检测要求，也不据此引入服务器中转。

### 4.5 验证门禁

正常、失败与边界测试均须覆盖：过期/撤销/被修改的计划、越权目标、提示注入、跨客户端句柄、敏感输出、审计缺段，以及 AI 建议试图改变授权的情形。任何绕过强制权限检查的路径均不通过验收。AI 增益评测只能补充安全证据，不能替代这些确定性检查。

## 五、功能提案深度分析

> #14 修订：保留功能方向与既有用户决策，修正依赖和低估的风险。本章是提案输入，不能替代正式 OpenSpec 设计或授权。

### 5.0 依赖关系总览

```
现有片段 CRUD + 终端选文 → 片段深化（不依赖完整操作历史）
现有 SSH exec + 授权/任务状态/审计 → 手动批量执行 → 巡检闭环
                                          ↑
命令历史的可核对命令 ──→ 后续复用入口（重新审核，不继承授权）
跳板机 ──→ 需要内网访问的任务（其他任务可先用直连主机）
已审核且成功验证的巡检计划 → 用户启用 macOS 定时巡检
```

授权、失败语义、资源限制和审计是受控执行的共同前置；原始终端录像、向量搜索、完整记忆与拓扑不是批量执行或 AI 增益实验的硬前置。

### 5.1 提案 1：本地命令历史与审计

**目标：** 本地命令执行历史作为审计记录，关联目标、会话/任务、操作者或调用主体、计划/授权、时间、命令、执行结果和验证证据；删除后能够清楚发现历史缺段。具体格式和存储方式在审计提案中详细设计。

**记录渠道与证据边界：**

| 渠道 | 可以记录的事实 | 限制 |
|------|----------------|------|
| 应用代发的 exec/批量/巡检 | 实际提交的命令、确定的目标、批准版本、结果状态 | 超时或断线不证明远端未执行；缺少退出状态时不能填零 |
| 手动交互 shell | 明确捕获到的命令边界、会话事件及其来源 | 原始按键受行编辑、TUI、嵌套 shell 影响，不能当作完整命令清单 |
| SFTP | 路径/目标、操作类别、冲突决策、终态等审计元数据 | 不默认记录文件正文，凭据与敏感内容须过滤 |
| 可选终端录像 | 已授权范围内的输出、尺寸变化、时间线 | 录像不能替代结构化审计；输出也可能含秘密 |

**命令边界：** 客户端代发命令可准确知道提交内容；交互命令优先利用 shell integration 协议信号，正则与手工标注仅补充。信号来自远端，不能作为可信身份或授权来源；不可辨识区域明确标记「命令覆盖未知」。嵌套 SSH 不凭一段文本自动更改主机身份或授予新目标权限。

SwiftTerm 提供界面选择和终端事件，审计规则、持久化和校验逻辑在 Rust；不把 Swift 的输入拦截点变成仅能记录 GUI 操作的业务实现。MCP 与调度入口也必须覆盖。

**连续性与删除：** 支持查看缺段的范围及可知原因，区分授权清理、异常缺失、证据不足和不可验证；合法删除不抹去清理留痕。学习系统只能消费允许的派生视图，不改写原记录或完整性结论。记录编号、完整性证明、删除留痕、轮转、备份恢复、崩溃修复与密钥管理，均留到提案设计。

**隐私与可信边界：** 不默认记录逐键输入；秘密不得进入一般审计内容。必要脱敏有明确标记，并保留非敏感关联元数据。须说明仅本地证据对整库替换、尾部截断与旧备份回滚的检测边界，不能宣称完整抵御本机管理员篡改；也不能因可被删除而取消审计定位。

| 阶段 | 内容 | 验收重点 |
|------|------|----------|
| 首个执行闭环 | 应用代发命令与 SFTP 审计、连续性检查、删除缺段展示 | 正常链路、失败/未知、缺段、篡改与写入中断；格式由提案决定 |
| 交互记录深化 | shell integration 与低置信标注 | 行编辑、多行命令、TUI、嵌套 SSH、伪造标记均不误报完整覆盖 |
| 按需求扩展 | 可选录像与回放 | 授权、脱敏、尺寸变化、资源限制与删除关联；不能阻塞最小巡检闭环 |

### 5.2 提案 2：代码片段深化

**已有基础：** Rust `Snippet`/`SnippetStore`、FFI 与真实 Swift 后端已经有列表/保存/删除实现；Swift `SnippetsView` 有编辑、复制等入口。应逐项验收与深化，不能重新列为全新能力。

| 能力 | 依赖与边界 |
|------|------------|
| 终端选文 → 片段 | 终端选择 API 与片段 CRUD 即可；不依赖操作历史 |
| 多级标签与搜索 | 复用现有 tags；处理旧数据与查询边界，见 5.7 |
| 编辑器体验 | 按用户反馈增加，不先建设完整 IDE |
| 参数化模板 | 先明确参数类型、引用与 shell 转义；不依赖完整历史，执行时仍重新审核 |
| 片段 → 批量任务 | 将具体片段版本展开进执行计划；保存的片段不是自动获批的命令 |

片段名称/ID、Markdown 正文与 Swift 展示字段需确定稳定映射。已审核任务固定引用内容，片段更新不能静默改变已授权计划；与巡检的引用关系见 8.7。

### 5.3 提案 3：远程命令批量执行

**已有原语：** `SshSession::exec` / `exec_with_timeout` 可非交互执行，收集 stdout/stderr 和可选退出码；默认等待超时为 60 秒。它是执行原语，不是完整任务引擎。

**必须补齐的契约：**

| 领域 | 要求 |
|------|------|
| 目标与审批 | 多选/分组解析成明确目标集合，展开参数后审核；AI 与历史选择不继承权限 |
| 执行状态 | 区分排队、等待批准、运行、成功、失败、超时、取消请求、已确认停止、结果未知 |
| 超时与取消 | 停止等待不等于远端已停止；未知结果保持可见，重连不自动重发 |
| 有界资源 | 主机并发、每主机步骤并发、输出大小、等待时间、总预算及背压策略 |
| 结果与恢复 | 逐主机终态、部分成功、崩溃恢复、重入核对；未收到退出码不得默认成功 |
| 重试与补偿 | 仅按明确的可重试条件与预算重试；任意 shell 命令不承诺恰好一次或通用回滚 |
| 业务验证 | 执行成功与目标完成分别判断；健康检查、版本核对等验证步骤也在计划中审核 |
| 连接所有权 | 任务拥有其 Transport 与句柄；不从终端标签隐式借用连接，关闭不影响其他所有者 |
| 审计 | 关联计划、批准、尝试和结果；连续性校验及缺段展示纳入同一闭环 |

**实施顺序：** 先用 fake SSH/时钟/存储测试正常、错误和边界行为；再实现手动输入、多选、有限并行与结果持久化；之后增加片段/历史入口、灰度批次与条件步骤。计划预览是审批前置，不延后到远期。

验收必须包含「远端已经执行、回包前断线」以及「用户撤销后尚有步骤排队」，确保不会盲目重试、误报成功或继续扩大执行。

### 5.4 提案 4：SSH 跳板机（Proxy Jump）

[已决] 采用方案 A：`HostConfig.proxy_jump` 引用已有主机 ID。方案 B（内嵌代理配置）保留为已比较替代：配置自包含，但需要额外凭据约定和嵌套模型；不作为当前方向。

```toml
# 候选字段；最终契约在 OpenSpec 提案中确定
proxy_jump = "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"
```

[已核对] 当前连接走 `connect_stream`，`CountingStream` 的底层为 TcpStream，尚无跳板配置。技术候选为 direct-tcpip 通道转为流后承载目标 SSH；不能把整个功能估计成仅替换流类型。

**设计必须覆盖：** 每跳独立凭据获取、未知指纹确认与变更阻断；自引用/环/最大链深；逐跳与整链超时、取消和部分失败清理；DNS 与目标身份归属；完整路径的审计和授权；连接及父链生命周期；配置导入导出中的 ID 重映射与悬空引用。

[建议] 删除被引用跳板机采用 RESTRICT，显示引用方并提供显式替换操作（14.9）。约束在 Rust 配置层统一实现，不能仅靠 UI 禁用按钮；导入和 MCP 入口也需遵循。

跳板链变化影响已经审核的任务，须按第四、十三章重新核验或失效，不能悄悄改走直连。

### 5.7 多级标签系统调研（代码片段分类）

[已决] 一个片段可有多个层级标签；使用 `/` 分隔路径；默认 OR，可切换 AND；frontmatter 保存路径字符串，`tags.toml` 保存索引。

```yaml
tags: ["网络/内核参数", "故障处理/生产事故", "性能优化/延迟调优"]
```

需补齐的设计边界：

- 旧标签可能本来含 `/`，需要明确迁移/转义规则，不能无条件称「零迁移成本」。
- 子树查询必须满足 `tag == prefix` 或 `tag.starts_with(prefix + "/")`，避免父标签漏匹配及同名前缀误匹配。
- 若 `tags.toml` 只存派生树，丢失可以重建；若还存颜色、描述、空标签等独立元数据，则必须有独立保存/恢复策略，不能同时宣称全部可重建。
- 父标签重命名涉及多个 Markdown 文件，需定义失败恢复与索引一致性；标签删除不删除片段正文。
- 路径规范化、空层级、重复标签、最大层级和 OR/AND 的空选择语义，纳入正常/异常/边界用例。
- 片段标签不能直接当作主机标签。主机多维选择仍需单独数据模型，并在审批时冻结最终主机集合。

UI 保留树形浏览、自动补全和标签管理方向；查询与变更规则统一在 Rust 核心。

### 2026-09-09 #2 — 四个功能提案深度分析

**背景：** 用户提出四个具体功能方向：操作历史、代码片段深化、批量执行、SSH 跳板机。

**技术调研结论：**
1. **操作历史**：拦截点明确（`TerminalCoordinator.sendToShell`），但命令边界检测是核心难点。建议分阶段：先做原始 I/O 日志和传输持久化（低风险），再做命令解析（高风险）。
2. **代码片段深化**：Rust/Swift 双侧已有基础实现，字段需对齐。终端选文 → 片段的路径清晰（SwiftTerm 支持 `selectedText`）。分类建议用标签而非文件夹。
3. **批量执行**：`SshSession::exec_command` 已支持非交互式单命令执行，并行执行只需多连接管理。建议先做手动命令 + 多选主机，后续再联动历史和片段。
4. **SSH 跳板机**：**可行性最高**。russh 原生支持 `channel_open_direct_tcpip`，当前代码已用 `connect_stream`，替换流来源即可。改动集中在 `SshSession::connect`。

**优先级共识（待确认）：**
- P0：SSH 跳板机 + 代码片段深化（分类 + 终端选文）
- P1：操作历史（原始日志）+ 批量执行（手动命令）
- P2：操作历史（命令解析）+ 联动功能

### 2026-09-09 #6 — 巡检功能设计决策

**背景：** 用户对巡检功能三个设计问题给出决策。

**决策确认：**
1. **巡检方案独立**：不是代码片段的扩展类型，而是独立功能实体。可在方案中引用代码片段（`SnippetRef`）。巡检方案 = 采集命令 + 解析规则 + 目标选择 + 阈值配置。
2. **数据库选型**：SQLite + sqlite-vec。调研了 DuckDB（移动端未就绪）、LanceDB（无 Swift 绑定）、SurrealDB（太年轻），SQLite 在数据量、绑定成熟度、iPadOS 兼容性上全面胜出。sqlite-vec 扩展支持向量搜索，为 Phase 2-3 的语义搜索做准备。
3. **报告格式**：应用内查看 + HTML 导出。不采用 PDF（静态格式，不支持交互）。HTML 可通过模板实现动态效果。

**新增数据模型设计：**
- `InspectionProfile`：方案定义（名称、标签、采集项、目标规则、阈值）
- `InspectionItem`：采集项（指标名、命令来源、解析规则、单位）
- `CommandSource`：内联命令或代码片段引用
- `ParseRule`：正则 / JSON 路径 / KV 格式

**数据库文件规划：** `~/.panda-ssh/panda.db` 统一存储巡检快照、操作历史、批量结果、传输历史、向量 embeddings。

### 2026-09-09 #11 — AI 原生能力缺口分析

**背景：** 用户指出 AI 原生平台缺少记忆系统，要求分析其他缺口并调研团队协作实现。

### 8.1 愿景声明

**Panda SSH：以原生 SSH/SFTP 工作区为基础，帮助用户更省力、更可核对地完成远程巡检与排障。**

[假设] 意图辅助、操作复用、证据比对和经验检索能够降低人工投入；是否增加长期记忆、拓扑或复杂编排，由任务实验决定。产品不改名，核心保持开源。

明确边界：用户掌握执行与外传授权；学习不扩权；本地命令历史作为可发现缺段的审计记录；定时任务只在 macOS 提供，iPadOS 不支持，也不通过服务器中转执行。

### 8.2 市场与差异化假设

[已核对，2026-09-09] Warp 于 2026-04-28 宣布客户端开源，当前官方文档列有远程 SSH Agent、文件编辑与审查能力。原稿「闭源、仅本地、仅命令补全」的竞品基线不成立。[开源公告](https://www.warp.dev/blog/warp-is-now-open-source)、[远程 SSH 能力](https://docs.warp.dev/terminal/warpify/ssh)

不再断言不存在「SSH + AI + 开源」竞品，也不把 AIOps 平台概括为「只看不动」。后续比较应覆盖 SSH 客户端、运维编排工具、AI 终端及用户现有脚本/MCP 组合，以具体任务为单位核对功能、权限、成本、远端依赖和平台支持。

| 候选差异 | 需要验证的证据 |
|----------|----------------|
| 低配置成本的原生远程工作区 | 新用户完成首个真实巡检任务需要的配置与人工步骤 |
| 受控执行与结果可核对 | 越权被阻断，失败/未知不冒充成功，审批负担可接受 |
| 可发现缺段的本地审计 | 中间删除可见，异常与合法清理可区分，可信边界明确 |
| AI 帮助减少人工投入 | 相同任务质量下减少查找、输入、修正与验证时间 |

这些是待验证的产品优势，不是市场空白证明。通用开发者调查不能替代 SSH 运维用户访谈或任务实验。

#### 三道验收关卡

| 关卡 | 验证对象 | 通过/失败标准 |
|------|----------|---------------|
| G0：基线统一 | 当前规格、实现与目标边界 | 冲突有明确解决且进入对应规格变更；尚有矛盾时不得以「基线已完成」放行依赖能力 |

#### AI 增益验证方案

- **比较对象：** 人工原流程、固定规则/模板流程、AI 辅助流程，使用相同任务集、输入证据与权限范围；避免只和刻意弱化的基线比较。
- **任务集：** 覆盖正常巡检、故障初筛、错误输入、权限不足、数据缺失/过期、断网、提示注入和历史缺段；保留独立验证案例，避免学习数据泄漏到评测。
- **记录指标：** 人工操作与查找时间、审批/修正/复核负担、任务总耗时、正确完成率、错误建议与错误操作、模型延迟/费用/资源消耗。把人工复核成本计入收益。
- **通过规则：** 提案在试验前确定任务规模、可接受误差与最小有意义改善幅度；在不降低任务完成质量的情况下，人工投入有可重复的实质下降；强制安全用例零越权，严重错误操作不放行。不能事后挑选有利指标宣布成功。
- **证据表达：** 报告样本量、适用环境、失败案例及不确定性；小样本只支持继续试点，不据此承诺生产可靠性或绝对安全。
- **迭代门禁：** 模型、提示、工具、Skill、记忆策略变化时运行受影响回归；无实质收益则保持简单方案，失败则回退候选版本。

Verification 包括 TDD、协议/状态/权限与审计检查，遵循仓库测试与覆盖率门禁；Validation 是真实任务收益与用户负担验证，不能以代码覆盖率替代。

### 8.7 巡检功能设计决策

#### 决策 1：巡检方案、执行计划与执行记录分开

巡检方案仍是独立功能实体，可作为领域化 Skill，引用片段；它不是已经授权的执行实例。

| 对象 | 内容与生命周期 |
|------|----------------|
| 巡检方案 | 采集项、适用环境、解析/阈值与验证规则；可编辑、版本化 |
| 具体执行计划 | 展开后的目标、身份、跳板路径、参数、引用版本、预算与验证步骤；审核绑定此对象 |
| 执行记录 | 每次运行的尝试、状态、指标、验证和审计关联；不被方案更新改写 |
| 定时任务 | 指向已经人工审核且成功验证的计划，加上用户启用的周期授权；仅 macOS |

片段或 Skill 更新不能使已经审核的巡检自动使用新内容。旧计划只有在引用被冻结且前提可核验时才可继续，新内容需重新审核和试跑。

每项指标需定义 key、单位、采样窗口、采集时间、适用系统与依赖、权限要求、解析版本、质量状态和验证规则。状态至少区分有效、不可用、不支持、采集失败、过期；部分失败不得把主机标为全部正常。网络/磁盘速率依赖时间差和计数器重置处理；跨主机比较需保留时间偏差。默认指标候选见 14.8。

#### 决策 2：结构化存储方向与审计设计解耦

保留 SQLite 作为巡检快照、任务结果和查询索引的选型方向。sqlite-vec 是语义检索候选扩展，待与关键词/结构化检索比较且通过目标平台构建与性能验证后引入；不因已经选型就先加载全部依赖。

原稿以「无 Swift 绑定」排除 Rust 可集成库的论据不充分；本项目已有 FFI，实际考察应为 Rust 集成、iOS 静态链接、资源预算、许可及维护成本。SQLite 的原生可用性也不证明其扩展已在所有目标平台可用。

**命令审计的存储方式和格式在专项提案设计，本文不要求全部放入同一个 panda.db。** 录像可单独存储并与审计关联。以主机数、采样项、频率、保留期和输出体积估算容量，不能仅凭「数十万条无压力」判断；纳入迁移、备份、崩溃恢复、保留与删除策略。

#### 决策 3：应用内查看与 HTML 导出

保留应用内报告与离线 HTML 导出方向，不增加 PDF 范围。远端文本是不可信数据，模板需进行上下文正确的转义，嵌入脚本的数据不能仅靠 HTML autoescape；导出不加载外部资源、不隐含外传。

报告展示指标单位、采集时间、来源、失败/未知项和相关审计缺段；避免制造完整性假象。模板与图表库作为候选在提案验证，内置模板只读，用户副本有版本与兼容性检查；不预设为可执行代码片段。

```
       有界执行 → 结果验证 → 审计与连续性检查
          ↑                       ↓ 受限数据视图
     规则与 AI 候选计划 ← 检索 / 可选记忆
```

业务规则始终位于 Rust；模型、Skill、记忆与远端输出都不拥有权限签发能力。

#### MCP Tools 与 Skills 的关系

MCP 负责能力交换，不保证业务无状态；SSH 连接与任务句柄本身有生命周期和所有权。Skill 是可复用的指令与资源包，确定性执行依赖另行定义的计划契约，不能从任意 Markdown 自动获得。详见第十一章。

#### Panda SSH 作为 MCP Server

[方向已决，契约待设计] 可逐步提供主机选择、计划提交/预览、已授权步骤执行、任务状态和结果等能力。只暴露明确批准的工具集合，不自动把全部 FFI 导出成 MCP；凭据读取/保存接口不对 AI 开放。

必须定义客户端身份、连接句柄归属、文件路径范围、授权生命周期、输出限制、数据返回范围、取消及重连行为。连接未知或变更主机密钥时保持确认/阻断流程。工具结果返回外部 Agent 也是数据跨边界，不能以「本地 MCP」免除检查。

[已核对] MCP 工具注解只是提示，不是强制权限控制；安全保证仍要靠执行端和隔离措施。[MCP 官方说明](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)

#### 外部 MCP Servers

K8s、Docker、日志与监控等集成按真实需求选取。对每个 Server 核对来源、版本、维护、许可、运行位置与权限；本地 stdio、HTTP 服务、远端 SSH 命令不是同一种部署边界。iPadOS 不假设能运行桌面端子进程，未支持的能力明确提示；不建设服务器中转执行来补齐平台差异。

#### Skill 定义格式（历史 YAML 草案）

> **已废弃，仅保留历史。** 以下两个 YAML 示例不是当前可执行契约，包含未经校正的旧阈值、参数插值与命令组合；不能用于实现或验收。当前格式与契约见第十一章，授权见第四、十三章。

```yaml
# 巡检方案就是一个 Skill
name: 日常巡检
tags: ["巡检/日常", "生产环境"]
description: 对生产环境主机执行常规健康检查

# Skill 可以引用的 MCP Tools 来源
mcp_servers:
  - builtin  # Panda SSH 内置的 SSH/SFTP tools

# Skill 的输入参数
inputs:
  - name: target
    type: string
    description: 目标主机分组或标签
    default: "env/prod"

# Skill 的执行步骤
steps:
  - name: 采集指标
    tool: batch_exec
    input:
      host_ids: "{{resolve_hosts(target)}}"
      command: "uptime && free -m && df -h && cat /proc/net/dev"
    output: raw_results

  - name: 解析结果
    action: parse_metrics
    input:
      data: "{{raw_results}}"
      rules:
        - metric: cpu_load
          pattern: "load average: (\\d+\\.\\d+)"
        - metric: mem_used_pct
          pattern: "Mem:.*?(\\d+).*?(\\d+)"
          expression: "$2 / $1 * 100"
        - metric: disk_used_pct
          pattern: "/dev/.*?(\\d+)%"

  - name: 存储快照
    action: store_snapshot
    input:
      profile_id: "{{this.id}}"
      metrics: "{{parsed_metrics}}"

  - name: 阈值检查
    action: check_thresholds
    input:
      metrics: "{{parsed_metrics}}"
      thresholds:
        - metric: cpu_load
          operator: ">"
          value: 80
          severity: warning
        - metric: disk_used_pct
          operator: ">"
          value: 85
          severity: critical

  - name: 生成报告
    action: render_report
    template: inspection_report.html
    output: report_html
```

**更复杂的 Skill 示例（故障排查）：**

```yaml
name: Web 服务故障排查
tags: ["故障排查/Web", "应急响应"]
description: 系统化的 Web 服务故障排查流程

mcp_servers:
  - builtin
  - elasticsearch  # 需要 ES MCP Server

steps:
  - name: 检查服务状态
    tool: ssh_exec
    input:
      command: "systemctl status nginx && systemctl status app"

  - name: 检查资源使用
    tool: ssh_exec
    input:
      command: "top -bn1 | head -20 && free -m && df -h"

  - name: 搜索错误日志
    tool: elasticsearch.search  # 通过外部 MCP Server
    input:
      index: "app-logs-*"
      query: "level:ERROR AND @timestamp:>now-1h"

  - name: 对比同组主机
    tool: batch_exec
    input:
      host_ids: "{{same_group_hosts}}"
      command: "curl -s -o /dev/null -w '%{http_code}' http://localhost/health"

  - name: 生成排查报告
    action: render_report
    template: incident_report.html
```

#### Skill 的来源与更新

内置、用户自定义和社区共享均可作为来源；来源不同不改变执行审批原则。导入与更新要检查包内容、依赖、权限和许可，固定执行引用版本；Skill 自带的 allowed-tools 不能成为授权。

#### 对能力架构的影响

内置执行能力使用 Rust 接口，FFI 与 MCP 共享同一约束。审计与可选记忆分开：前者记录操作和完整性状态，后者提供可纠正的候选知识，不能反向改写审计或授权。

#### 对演进路线的影响

MCP 可在 G1 通过后以少量工具进入 Phase 1 验证，但不再以「封装成本小」直接放行。薄 AI 辅助试点不必等待 Phase 3 全功能 Agent；复杂工作流、外部 Server 与社区平台按增益和需求渐进建设。

#### AI 模型策略

保留本地模型、用户自带 API Key 和混合模式的产品方向。先验证一个可用配置与目标任务，再扩展 provider；本地设备模型的内存、延迟、运行环境、许可及 embedding 版本迁移在提案中核对。

AI/MCP 层不能读取凭据；密钥通过受控配置与连接适配使用。云端 provider、输入数据范围与用途须用户授权；本地失败不静默切换云端。模型选择或学习质量变化均不改变执行权限。

### 10.3 场景驱动的 Skill 规划

#### 内置 Skill 候选

保留日常巡检、深度巡检、批量命令执行、日志检索、性能诊断、安全合规六个方向。第一批只完成一个巡检闭环及一个排障验证样例，其余按需求排序，不把六个同时交付作为阶段门槛。

Skill 是方案入口，执行时生成明确计划并经审核。定时巡检仅 macOS，且需首次人工审核、人工执行验证无问题后由用户启用。批量变更、清理或修复不因使用 Skill 而自动取得周期授权。

#### 扩展 Skill 候选

K8s、容器、数据库、滚动部署与跨系统日志等按真实环境另立提案。先确认工具权限、版本、数据边界及失败恢复，再选择 MCP Server；「存在 MCP Server」不等于场景已完成。

### 10.4 场景驱动的产品能力缺口

| 能力 | 必须先说明的契约 |
|------|------------------|
| 审计 | 本地命令历史、连续性检查、删除后缺段可见；格式/存储后续设计 |
| 批量执行 | 有界资源、部分失败、取消、结果未知、重试与业务验证 |
| 恢复 | 标签/显示恢复、SSH 重连、远端进程恢复分别承诺 |
| 定时巡检 | macOS 准入与授权失效，退出/睡眠/错过/重叠策略；iPadOS 不支持，无服务器中转执行 |
| 跨主机同步 | 单向或双向、内容比较、冲突、删除传播、符号链接、权限/元数据、部分失败、临时落地数据及带宽 |
| 主机选择 | 主机标签与片段标签分开；分组选择在审批时固定为具体集合 |
| 环境兼容 | 远端操作系统、工具版本、locale、权限与依赖缺失，不能全归为一个正则问题 |

### 10.5 场景 × 验证关卡

| 场景组 | 首要验证 | 扩展条件 |
|--------|----------|----------|
| 巡检与批量采集 | G1：授权、有效测量、结果未知、审计缺段 | 首次人工验证成功，用户才可启用 macOS 定时 |

## 十一、Skill 开源标准调研

> #14 修订，公开资料核对日期：2026-09-09。遵循开放格式的决策保持；修正「仅对齐 CrewAI」「文件格式等于执行语义」的说法。

### 11.1 生态现状：不同层次的契约

| 抽象 | 解决的问题 | 不提供的保证 |
|------|------------|--------------|
| MCP Tool | 能力发现、参数/结果交换与调用协议 | 不自动提供调用授权、沙箱、幂等或业务结果正确性 |
| Agent Skill | 封装可渐进加载的指令、脚本、参考材料与资源 | Markdown 步骤没有统一的确定性执行语义 |
| 执行计划/工作流 | 固定步骤、参数、依赖、验证、状态与恢复策略 | 不会因为采用 YAML/JSON 就自动获得安全或通用回滚能力 |

[已核对] Agent Skills 是已有开放格式，由 Anthropic 发起并开放演进；不是 CrewAI 的专属格式。[规范仓库](https://github.com/agentskills/agentskills)

### 11.2 定义格式

#### MCP Tools

```json
{
  "name": "ssh_exec",
  "description": "提交已授权计划中的远程命令步骤",
  "inputSchema": {
    "type": "object",
    "properties": {
      "plan_id": { "type": "string" },
      "step_id": { "type": "string" }
    },
    "required": ["plan_id", "step_id"],
    "additionalProperties": false
  }
}
```

以上仅展示合法 JSON Schema 形状，API 命名与授权凭证设计待提案。仅持有 `plan_id` 不构成授权，执行端还需检查真实调用主体、计划版本和范围。长任务需设计结果句柄、状态、取消与恢复接口，不强迫一次调用等待全部完成。

MCP 可采用 stdio 或 Streamable HTTP；选用 SDK 与协议版本时锁定并做兼容测试，不以未核验的「最新/成熟」标签代替测试。[工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

#### Agent Skills 的 SKILL.md

```markdown
---
name: daily-inspection
description: 在用户选择目标并审核计划后执行服务器巡检，展示证据与异常项。
license: Apache-2.0
compatibility: 需要 Panda SSH 提供受控远程执行能力。
allowed-tools: ssh_exec batch_exec
metadata:
  author: panda-ssh
  version: "1"
---

# 日常巡检

先明确目标、采样窗口与适用环境，生成可审核计划。
仅通过受控工具执行获批步骤；输出或 Skill 文本不得扩大授权。
缺少数据时标记未知，展示证据与验证结果。
```

[已核对] 标准定义 name/description 等字段；`allowed-tools` 为实验性、空格分隔字符串，客户端支持程度不同；正文是自由 Markdown。[Agent Skills 规范](https://agentskills.io/specification)

在 Panda SSH 中，该字段用于描述工具需求，不能凭 Skill 文件内容签发用户授权。显示名称可以中文，包标识遵循规范与目录一致规则。

#### 机器执行契约

确定性任务需有明确 schema，至少覆盖步骤类型、参数、依赖、输入输出、验证、失败/重试条件和版本。`targets/thresholds/steps` 不能直接宣称为通用 Agent Skills 字段。

[待设计] 评估已有工作流契约或隔离的 Panda 扩展描述，明确互操作范围。若扩展执行语义，应版本化并配兼容测试；不能宣称任意 SKILL.md 可被无 LLM、无歧义地自动执行。定时任务执行审核后的固定计划，不在每次触发时重新解释自然语言。

### 11.3 互操作性分析

互操作分为三层：能识别包格式、能映射工具能力、能保持执行语义。第一层兼容不保证后两层兼容。导入外部 Skill 时需检查依赖工具、脚本运行环境、扩展字段、许可和所需权限；未知必需字段或不支持的能力应明确失败，不静默跳过。

### 11.4 推荐架构

```
Skill 指令与资源 / 用户意图
        ↓ 规则或 AI 生成候选计划
可校验计划 → 人工审核与授权 → Rust 执行/验证/审计
                                    ↑
                            FFI 与 MCP 适配入口
```

执行引擎使用 Rust 内部接口调用内置能力；MCP 是外部适配层，不强制内部绕行协议。AI 可提出后续诊断候选，但新增步骤须重新审核；确定性运行部分不得被自然语言输出改写。步骤输出是数据，不作为可自动求值的代码或授权。

### 11.5 Skill 目录结构

```text
skills/
└── daily-inspection/
    ├── SKILL.md
    ├── references/
    ├── assets/
    └── scripts/          # 可选，运行环境与授权需单独审查
```

具体执行描述文件的位置与格式留待提案。禁止默认运行导入时脚本或钩子；更新不能改变正在使用的已审核版本。iPadOS 不假设具备本地 shell/任意子进程能力，未验证的脚本或 stdio 工具明确不支持。定时能力只在 macOS 提供，不通过远端服务补齐。

### 11.6 与现有架构的集成

| 组件 | 边界 |
|------|------|
| 代码片段 | 计划引用具体内容版本；修改片段不改变旧授权 |
| 巡检方案 | 可作为领域化 Skill 入口，生成明确的采集与验证计划；数据契约见 8.7 |
| 批量执行 | 使用共同任务状态与授权，不创建另一套绕过审计的执行路径 |
| 审计 | 记录实际执行、审批与结果；Skill 不得控制记录删改或完整性结论 |
| 记忆 | 提供来源明确的候选经验，不能写授权或启用调度 |
| 平台适配 | 负责 UI 与平台服务，业务判断仍在 Rust；iPadOS 不支持定时任务 |

### 11.7 待确认与验证

状态统一在第六章追踪。保留六个内置 Skill 候选（日常巡检、深度巡检、性能诊断、安全合规、批量执行、日志检索），但不要求首版同时完成。先以日常巡检和一个排障样例验证计划生成、审批、执行和证据展示；安全合规输出不在未经基准验收时宣称认证合规。

确定性 schema、包版本锁定、工具命名映射、平台兼容与恶意输入用例在提案中设计。格式兼容验证与用户任务增益验证分别实施，后者采用 8.5 关卡。

## 十二、AI 原生能力缺口分析

> #14 修订：记忆、拓扑和主动感知是候选能力，不是「AI 原生」必须一次建齐的清单。按可验证增益投入，学习不得越过第四章安全边界。

### 12.1 记忆系统（Memory System）

已有记录经过检索即可为后续会话提供上下文，不能说「没有独立记忆层就必然每次从零开始」。独立记忆系统的价值应通过相关性、人工查找时间与错误经验复用率验证。

| 类型 | 内容 | 生命周期与证据 |
|------|------|----------------|
| 工作上下文 | 当前任务、已检查项、待验证假设 | 任务级；摘要保留来源，不能把缺失证据补成事实 |
| 情景记忆 | 故障现象、操作、验证结果、用户修正 | 记录环境与证据范围；成功经验与候选经验分开 |
| 语义记忆 | 环境约束、已确认依赖、用户偏好 | 显式来源、有效期、更新与冲突处理 |

[建议] 先使用结构化记录、人工标注和关键词检索；检索基线不足时再验证 embedding 与 sqlite-vec 的增益。数据存储不直接等于记忆质量，也不意味着模型参数已经学习。

记忆须携带来源、时间、主机/环境作用域、版本、置信度和有效性。对冲突保留证据差异；源审计被删除或存在缺段时标记证据不完整。记忆可检查、编辑、关闭和删除，但这些操作不修改原审计；去重、索引删除与备份策略在提案中设计。

### 12.2 环境拓扑模型（Environment Model）

[假设] 显式依赖能帮助缩小排障范围；依赖图本身不能证明故障因果，也不能自动决定部署顺序。例如 DB、Cache、Web 的变更顺序受兼容性、迁移方案和故障模式约束，不能固定为「先 DB 后 Web」。

区分声明的依赖、实际观测的连接与 AI 推断的候选关系。行为推断只进入建议队列；`ssh` 或 `mysql` 文本不是目标身份或依赖的证明。主机分组、网络可达性、应用依赖和授权集合是不同概念。

[建议] 从人工声明的少量关系开始，观测附时间与来源；需要探测时由用户审核具体范围。没有授权的后台扫描不属于路线。只有在跨主机诊断样例上证明收益后，再增加自动发现与图查询复杂度。

### 12.3 反馈学习回路（Feedback Loop）

```
候选建议 → 人工审核/修正 → 受控执行 → 独立结果验证 → 候选经验 → 增益评测
```

| 信号 | 可核对事实 | 不能直接当作标签 |
|------|------------|------------------|
| 退出码/输出 | 执行返回的状态 | 故障已经解决 |
| 用户修正 | 用户改变了哪些内容 | 可在所有环境推广的新规则 |
| 告警忽略 | 用户未处理该提醒 | 该告警一定误报 |
| 故障恢复时间 | 观察到恢复的时间 | 恢复一定由 AI 的建议造成 |
| Skill 步骤失败 | 在具体环境中失败 | 必须自动修改流程或权限 |

候选阈值、模板和步骤调整先做离线回放或影子评估，再由用户采纳。模型、提示、规则或记忆版本改变后运行相关回归集；不通过则撤回候选。授权、调度启用和审计连续性均不属于学习可修改对象。

### 12.4 主动感知与注意力机制（Proactive Awareness）

| 能力 | 当前允许方向 | 边界 |
|------|--------------|------|
| 历史上下文提示 | 用户打开主机时展示已有记录 | 标注数据时间和缺段，不自动发新远程命令 |
| 模式建议 | 基于允许的上下文建议检查项 | 提示不等于执行授权 |
| 周期性远程采集 | 仅作为已获准的 macOS 定时巡检 | 首次审核并验证成功后启用；iPadOS 不支持 |
| 异常提醒 | 对已授权采集结果做规则判断 | 不以「只读」跳过授权，不自动提高采集频率或扩主机范围 |

提醒可关闭；数据过期、采集失败和任务暂停须可见，不能当作主机健康。自适应采样如有必要，应把频率范围与预算纳入审核计划，而非由模型自行决定。

### 12.5 团队协作（Team Collaboration）— 调研与设计边界

#### 调研对象与证据

原稿对 Claude/Warp/Windsurf/ChatGPT/Cursor/Copilot 的共享记忆和实时协作做了未经逐项版本核验的比较，#14 不再把该表当作事实。后续若进入团队功能提案，应记录具体版本、套餐、共享对象、权限和官方来源，不能混用「共享规则」「共享对话」「个人记忆」与「团队记忆」。

#### 团队协作机制

| 对象 | 可行候选 | 边界 |
|------|----------|------|
| Skill/SOP | 用户自有 Git 仓库 | 拉取、安装、启用与执行是不同动作；内容更新不扩权 |
| 故障案例 | 脱敏、显式发布的文本 | 保留来源与适用范围；不得默认上传审计或录像 |
| 环境声明 | 版本化文档与审查流程 | 冲突不可静默合并为事实 |
| 个人偏好/记忆 | 默认本地私有 | 不因加入团队自动共享 |

#### 关键判断

开源不会自动保证数据主权或秘密不外传。Git 加密传输也不等于仓库内容端到端加密；历史版本可能保留被删除的内容，需要明确共享、撤销、保留与清理范围。可同步经选择的文本对象，不直接共享或合并运行中的 SQLite 文件。

#### Panda SSH 团队协作设计建议

[建议] 暂缓团队基础设施，先支持明确范围的导入导出。需要团队功能时，从显式发布的 Skill/案例开始，考虑访问控制、来源与版本、冲突解决和撤销。当前路线不建设服务器中转执行服务；知识仓库不是定时任务执行端。

### 12.6 对架构和路线的影响

#### 架构更新

```
UI / MCP / 调度入口
        ↓
计划与授权 → Rust 受控执行 → 验证 → 审计
        ↑                         ↓ 只读、脱敏且保留来源
规则 / AI 候选建议 ← 允许的记录与派生记忆
```

权限检查是强制执行边界；记忆是可替换的数据能力，不要求成为所有调用的中间层。AI 不能写入授权或原始审计。

#### 路线影响

|------|----------|
| Phase 1 | 使用任务上下文与可核对记录，先证明人工巡检闭环及薄 AI 实验的价值 |
| Phase 2 | 基于实际反馈增加 Skill 复用与 macOS 定时，不要求先有向量/拓扑 |

## 十三、三条执行主线与自我迭代学习

> #14 修订：本章描述产品生成或编排的任务；手动交互终端仍可直接操作，并按明确的覆盖范围记录审计。统一授权原则见第四章。

### 13.1 三条执行主线

```
macOS 定时巡检：计划 → 人工审核 → 人工试跑 → 验证无问题 → 用户启用定时
一次性批量任务：计划 → 人工审核 → 有界执行 → 逐目标验证与审计
紧急排障任务：证据与候选方案 → 人工审核 → 执行 → 验证 → 必要时重新规划
```

#### 主线 1：定期巡检（仅 macOS）

| 阶段 | 行为 | 准入/退出条件 |
|------|------|--------------|
| 1.1 定义任务 | 选择目标、身份、跳板链、巡检内容、参数和结果验证规则 | 冻结具体目标集合及引用版本；分组变化不得自动扩大范围 |
| 1.2 首次人工审核 | 展示每台主机实际命令、权限、必要数据流向、预算与验证步骤 | 审核对象与执行对象为同一计划版本 |
| 1.3 人工试跑 | 执行已审核计划，保留审计与逐项结果 | 无执行异常且必要后置检查通过；异常指标是否符合任务预期按巡检规则判断，不只看 exit code |
| 1.4 用户启用定时 | 用户将已审核且验证无问题的计划放入定时任务，并确定周期与授权范围 | 不能只生成命令就启用，不能由 AI 自动批准或启用 |
| 1.5 定时执行 | 调度器检查授权及前提，执行同一已验证计划并审计结果 | 不重新生成命令，不静默替换脚本，不越过资源预算 |
| 1.6 失效与恢复 | 暂停、撤销、变更或异常进入可见状态 | 计划实质变化须重新审核、试跑并启用；结果未知不盲目重试 |

**执行计划与成功记录绑定：** 缓存内容至少涵盖命令、参数范围、目标、身份、跳板路径、脚本/片段/Skill 依赖及验证契约。仅缓存文本不能证明下次语义相同。具体标识、冻结方法、持久化结构与安全检查放在后续提案。

**变更处理：** Skill 出现新版本不自动替换运行版本；只有旧依赖确实被冻结、可核验且授权仍有效时才可继续旧计划，不能仅点选「忽略过时提示」绕过检查。新增主机、改变身份、引用内容变化等需重新准入。

**平台与运行期：** iPadOS 不创建、不启用、不触发定时任务，也不做回前台补跑；若读取到任务定义，仅展示不支持状态。当前不为定时任务提供服务器中转执行服务。macOS 首版建议限定应用运行且系统可调度期间；退出、睡眠、锁定凭据等情形的状态、通知与错过策略在提案中明确，不承诺全天候准点执行。默认不把错过的历史巡检伪装成已经完成，也不把恢复后采样标成过去的时刻。

**故障与重试：** 区分未发出操作与发出后结果未知。仅对已定义为可安全重试且仍获授权的步骤执行有限重试；策略、次数和预算需经过同一计划审核。任务重叠、资源不足或授权不可核验时不扩大并发或权限。暂停、撤销和计划失效均留审计记录。

#### 主线 2：一次性批量任务

| 阶段 | 行为 |
|------|------|
| 选择目标与命令 | 主机列表/分组解析为确定集合；命令可来自手动输入、片段或已有可信度标记的历史 |
| 生成与审核 | 展示逐目标计划及验证方式；展开变量后审批，禁止字符串拼接造成参数越界 |
| 有界执行 | 限制并发、输出、时间和资源；逐目标保存状态，不将部分成功汇总为全部成功 |
| 验证与审计 | 展示成功、失败、取消、结果未知及后置检查结果；中断后先核对远端状态再决定恢复 |

从历史选择命令不继承原授权；目标或环境改变后重新审核。UI、MCP 和 Skill 入口遵循相同规则。

#### 主线 3：紧急任务

| 阶段 | 行为 |
|------|------|
| 收集现象 | 用户描述问题；系统展示已有证据的来源、时间和适用范围 |
| 形成候选方案 | AI 或规则提出竞争假设、检查步骤和预期结果；资料不足时明确未知 |
| 审核与执行 | 人工审核具体命令及目标后执行；紧急状态不扩大授权 |
| 结果验证 | 用独立后置检查或人工确认判定是否解决；未解决则记录证据并重新规划 |

### 13.2 自我迭代学习

```
建议 → 人工审核/修正 → 受控执行 → 结果验证 → 候选经验 → 离线评测/人工采纳
```

[已决] 学习只改进建议与知识，不拥有授权写入、定时启用、安全策略修改、审计改写能力。

| 信号 | 可用于什么 | 不能直接推断什么 |
|------|------------|------------------|
| 用户修正命令 | 生成候选偏好或错误模式，记录原因及环境 | 原命令必然错误、修正可推广到所有主机 |
| exit code 与执行输出 | 记录执行层结果 | 业务问题已经解决 |
| 用户确认与独立后置检查 | 在证据范围内标记已验证案例 | 对其他版本/环境也必然适用 |
| 忽略告警 | 了解交互负担，提出阈值调整候选 | 告警一定误报，应该自动放宽阈值 |
| 反复成功执行 | 评估建议可靠性与人工投入 | 可以自动扩大目标、工具、参数或授权有效期 |

经验应带来源、时间、环境版本、置信度和适用范围。用户可检查、纠正、停用或删除派生记忆；这些操作不改写原审计记录，源证据删除后须标记缺失并处理派生索引。

**增益验证：** 以 8.5 的评测关卡比较改进前后人工投入、正确完成率、修正负担与安全违规。新候选未通过验证不提升为默认执行方案；收益不明显或错误增加时撤回候选，保持已有稳定流程。

### 14.2 命令边界检测（#7）

[设计方向] 应用代发命令可记录其确切提交内容；交互 shell 输入会经过行编辑、补全、多行语法与 TUI，原始按键不能直接还原完整业务命令。协议信号优先、正则与人工标注作为补充，所有来源标明可信度与覆盖范围。

OSC shell integration 依赖远端 shell 发出信号；集成脚本、客户端包装、终端组件解析版本与支持 shell 的组合须在提案做兼容验证。不能把远端可伪造的标记当作可信审计身份或授权。提示符正则、alt-screen 等只能作为启发式，不保证识别全部交互程序。[iTerm2 shell integration](https://iterm2.com/documentation-shell-integration.html)

测试应覆盖行编辑、多行/粘贴、无 echo 输入、TUI、嵌套 SSH、tmux、自定义提示符、伪造 OSC、编码与流分块。无法判断的片段标记未知，不自动归属到新主机。远端脚本安装或注入不属于默认获准操作。

### 14.3 审计与会话回放（#25、#35）

[已决] 命令执行历史作为本地审计记录；删除后须清楚发现历史中缺失的片段。存储方式、文件/数据库布局、连续性校验和删除留痕在审计专项提案详细设计，不能由录像格式提前决定。

[已核对] asciicast v2 描述时间、输出/输入、marker 与尺寸变化事件，可作为录像交换格式候选；官方默认不采集键盘输入。[v2 规范](https://docs.asciinema.org/manual/asciicast/v2/)

[待验证] v2/v3 兼容与 SwiftTerm 回放实现需要按项目实际版本核对。相对时间可以建立累计索引，不能仅以「v3 使用时间间隔」排除；定位到事件不等于恢复终端状态，seek 仍需重放或状态检查点。[v3 规范](https://docs.asciinema.org/manual/asciicast/v3/)

审计提案必须覆盖中间删除、尾部截断、修改/重排、清理、轮转、写入中断及旧副本恢复；分别说明可检测条件和无法验证的边界。不预选哈希链或具体格式，也不承诺只凭可整体替换的本地材料证明所有篡改。缺段展示不得泄露已清理的秘密。

录像为可选补充：即使只录输出也需授权和敏感处理；变速、尺寸变化、编码分块、长会话资源限制及删除关联须验证。审计连续性优先，录像不阻塞最小执行闭环。

### 14.4 定时触发（#26、#38）

[已核对] Apple 后台任务由系统决定运行时机，不能据此承诺准点 cron。[Apple 后台策略](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)

[已决] **iPadOS 不支持定时任务**，不提供前台定时、后台定时或回前台补跑，也不通过服务器中转执行。当前优先解决 macOS 本机定时巡检；这是明确产品边界，不继续寻找平台绕行方案。

[已决] 准入顺序为首次人工审核 → 人工执行 → 结果验证无问题 → 用户放入定时任务。仅执行同一已审核、已验证计划；原来的「生成命令即可定时」「可信模式直接执行」不再适用，详见第十三章。

[候选] croner 或其他表达式解析库与既有 tokio runtime 可作为 macOS 实现选项；库、持久化与调度循环在提案中验证，不断言生态里没有其他方案。

需设计：时区与夏令时、时钟回拨、任务重叠、退出/睡眠、错过触发、凭据锁定、暂停/撤销、授权失效、结果未知与有限重试。首版建议限定 App 运行且系统可调度期间，不承诺系统级常驻服务。错过的巡检须记录缺测；是否补一次由明确的用户策略决定，前提与授权仍有效，不能重放一串过期操作或伪造历史采样时间。

### 14.5 记忆系统设计（#27、#28、#29）

[建议] 先建立结构化经验、来源、有效性和关键词检索基线；sqlite-vec 作为已选方向中的可选增强，实测有收益才引入。不能把若干框架的架构归纳成所有系统已经收敛，也不直接迁移其他领域检索权重。

提炼优先采用用户标记、确定性字段和可核对规则；LLM 产物保留为候选，记录输入证据、模型/规则版本及适用范围。云端提炼须明确本次允许数据与接收方，不以「豁免会话」解释为无限外传。

遗忘需分别定义检索降权、事实失效和实际删除。原稿固定衰减系数及「不做物理删除」不再作为通用结论。用户清理、源证据删除、索引重建和备份保留分别设计；派生记忆删除不改写审计连续性，审计缺段使相关经验的证据完整性降级。

验证重点为检索命中、错误记忆召回、跨环境误用、人工纠正成本，以及相对简单基线的净增益。记忆和学习不能写权限、审批状态、调度开关或原始审计。

### 14.6 拓扑发现与团队同步（#30、#31）

[建议] 从人工声明的少量依赖开始；明确区分设计依赖、运行观测与 AI 推断，所有关系带来源和时间。轻量探测也需审批具体范围，不做未授权后台扫描；行为推断只生成候选，不能自动改写主机身份、授权集合或部署顺序。

拓扑有助于生成与排除假设，但不能凭一条依赖边证明根因。验证需包含过期关系、共享依赖、多重原因与反例。

团队知识可考虑用户自有 Git 仓库，但只同步显式发布的 Skill/SOP/脱敏案例，不直接同步活跃数据库、凭据或原始审计。更新、冲突、访问控制、撤销及历史秘密清理另行设计。知识同步不等于提供服务器中转执行服务，团队功能也不用于补齐 iPadOS 定时限制。

### 14.7 主动感知指标采集（#32）

[修订] 不把现有连接监控等同于远程主机指标采集，不以「只读」免除授权。手动巡检执行审核后的采集；周期采集归入仅 macOS 的定时巡检。iPadOS 只保留手动触发和基于已有记录的提示，不暗中建立周期任务。

[候选] 低频、有限并行的 exec 采集可以先验证。采集任务明确拥有其连接；需要长连接时复用该任务自己的 Transport，不跨所有者借用终端连接。任务暂停/结束释放自身资源，不影响其他会话。

采样频率、并发、输出上限、保活、重连和重试预算在提案按主机规模评估。异常时提高采样频率必须已包含在审核范围内，AI 不能自行加频。连续越限、恢复阈值和提醒冷却可作为规则候选，须经真实数据验证；不直接照搬原稿 60s/15s 等常数。

### 14.8 巡检指标与 HTML 模板（#23、#24）

#### 测量契约优先

先明确指标定义，再选择采集命令和阈值。以下保留十个默认候选方向；不是已经验证的跨发行版命令集，也不是全部必须进入首版。

| # | 指标 | 必须定义的测量与失效边界 |
|---|------|------------------------|
| 1 | CPU 利用率 | 指定时间窗口与采样方法；单次 top 不能直接宣称五分钟统计；计数器重置处理 |
| 2 | 负载/核 | load average 与 CPU 百分比是不同量；明确 1/5/15 分钟、核数与容器配额口径 |
| 3 | 内存使用率 | 明确 available/总量定义，工具版本和缺失字段，不用显示列名猜测语义 |
| 4 | Swap | 未配置 swap 与 swap 耗尽分开；分母为零不可当作告警百分比 |
| 5 | 文件系统容量 | 保留挂载点、字节/比例，考虑只读、临时与网络文件系统 |
| 6 | inode | 文件系统是否支持、总量为零及缺失值 |
| 7 | 失败服务 | 是否存在 systemd、服务范围、权限及关键性；数量不能替代影响等级 |
| 8 | 僵尸进程 | 采样时刻、进程状态定义、持续性与查询开销 |
| 9 | 时间同步 | 偏移数值与「是否启用同步」分开；不支持/无数据单列 |
| 10 | 登录失败 | 明确日志来源、服务名、时间窗口、权限与轮转覆盖范围 |

通用记录字段包括单位、采集时间与窗口、来源/版本、主机环境、质量状态、解析错误及审计关联。跨主机分析保留时间偏差；缺失、过期或权限不足不能记为零或正常。

阈值按环境配置，先使用可解释规则，之后以误报/漏报和处置成本验证。原稿「对标 Zabbix」的数值与窗口尚未逐项复核，不当作官方默认值或通用安全阈值。

#### HTML 模板

minijinja 与 uPlot 保留为候选，待平台打包、资源占用与兼容验证。模板转义必须考虑 HTML、属性、URL 和脚本数据上下文，不能只开启 autoescape 就宣称安全。远端文本始终按不可信数据处理。

输出单文件离线报告，不加载外部资源；导出前明确目标与内容范围。展示采集失败、数据过期、证据缺失与审计缺段，不能制造完整报告假象。内置模板只读、用户副本可编辑；实际路径、模板版本与回退行为在提案中设计，不把用户可写目录直接称为安装期只读。

### 14.9 跳板机删除引用处理（#12）

[建议] 使用 RESTRICT：被引用时阻止删除，列出引用方，提供用户明确发起的替换引用操作。该约束在 Rust 配置层实施，覆盖 UI、导入与未来 MCP，不靠界面按钮保证一致性。

替换需验证引用存在、无环且链深合法，不能静默清空 proxy_jump 改走直连；同时核对既有任务计划的路径变化，使旧授权按规则失效。引用图、批量更新原子性、崩溃恢复及导入 ID 映射在提案中细化。
