## 一、产品现状快照

| SFTP 文件传输 | **高** | 双栏浏览、批量传输、目录传输、冲突处理、速度显示、自动刷新、文件删除 |

| 安全 | **中高** | Host key 首次信任 / 变更告警、密钥指纹 SHA256、密码不落盘 |
| 连接监控 | **中高** | 内存快照、分层会话可观测、按需健康检查、遥测隐私边界 |
| 工作区 | **高** | 多标签（终端 + SFTP）、macOS/iPadOS 统一 chrome、上下文菜单、传输窗口 |
| 代码片段 | **预留** | 规格已定（Markdown 存储），未进入实现排期 |

### 1.2 技术架构

```
SwiftUI (macOS + iPadOS)
    ↓ AppBackend 协议 / FFI
panda-ffi (uniffi 绑定, 同步导出, 全局 tokio runtime)
    ↓
panda-core (Rust: 配置/分组/SSH/SFTP/主机密钥/遥测)
```

- 开源协议：Apache-2.0
- 安全模型：密码/私钥口令只存系统钥匙串，TOML 不落密钥材料，连接监控不记录敏感内容
- 平台条件编译：仅用于 UI 差异和平台服务，业务逻辑全部在 Rust 核心

## 二、AI 时代关键判断

### 判断 1：终端需要被重新定义

传统终端是透明管道（用户输入 → 服务器输出，中间零智能）。AI 正在改变这一点：

- **Warp**：AI 作为终端核心卖点（命令补全、输出解释、错误诊断）
- **GitHub Copilot CLI**：自然语言 → shell 命令
- **Aider / Claude Code**：AI 直接在终端中操作代码

**Panda SSH 的差异：** 目标是远程服务器管理，不是本地开发终端。远程场景下 AI 的价值不在于「帮你写命令」，而在于**降低远程操作的认知负荷和风险**。

### 判断 2：安全红线决定 AI 集成方式

当前安全模型约束：
- 终端输出 **不能** 默认发送给第三方 LLM API（可能含敏感数据）
- 命令建议 **不能** 依赖云端推理（除非用户明确授权）
- AI 功能必须走 **本地模型** 或 **用户自带 API key + 明确授权**

### 判断 3：差异化不在模型，在工作流

开源 SSH 客户端接入 AI 没有护城河。真正的差异化：
- 对 SSH/SFTP 工作流的深度理解
- 与连接监控、主机管理、文件传输的无缝集成
- 在安全边界内提供恰到好处的智能辅助

| 终端搜索 / 回滚 | 中 | 基础终端体验 | 待规格 |

### 第二层：本地智能辅助（近期 → 中期）

> 原则：不触碰安全红线，本地、可审计、用户可控。

|------|------|----------|------|

| **SFTP 智能文件操作** | 自然语言描述文件操作意图 | 生成操作计划，用户确认后执行 | 中 |

## 四、安全边界与约束原则

> 2026-09-09 更新：原"明确不做的事"清单已根据 MCP + Skills 架构升级（#7）调整为安全边界原则。不是绝对禁止，而是明确在什么条件下可以突破。

| 原则 | 边界 | 突破条件 |
|------|------|----------|
| **远程操作不可自动执行** | AI 生成的命令、Skill 步骤 **必须经用户确认** 才执行 | 仅当用户显式启用「自动模式」且操作为只读（巡检采集、日志查看）时可跳过确认 |
| **终端内容不默认外传** | 终端输出 **不默认发送给任何外部服务** | 用户主动触发（如"AI 摘要"）且明确选择 provider 后可发送；敏感操作默认走本地模型 |
| **凭据安全红线不变** | 密码/私钥口令只存系统钥匙串，TOML 不落密钥材料，AI 层 **不可访问凭据** | 无例外 |
| **AI 辅助不替代规则引擎** | 可用规则引擎解决的问题（错误诊断、阈值告警、格式解析）**优先用规则引擎**，更快更可靠 | AI 仅在规则引擎无法覆盖的场景（语义理解、跨主机关联、趋势预测）介入 |
| **Skill 执行可审计** | 每个 Skill 执行的步骤、调用工具、输入输出 **必须记录到操作历史** | 无例外 |
| **开源核心不分裂** | MCP + Skills 架构作为核心能力留在开源版本中，不做闭源独占 | 社区共享 Skill 遵循 Apache-2.0 |

## 五、功能提案深度分析

> 2026-09-09 #2 讨论新增。四个功能提案的技术可行性、依赖关系和优先级分析。

### 5.0 依赖关系总览

```
[1] 操作历史 ──→ [3] 批量执行（按主机组织历史，选取命令复用）
     │
     └──→ [2] 代码片段深化（选中文本 → 加入片段）

[4] SSH 跳板机 ── 独立，不依赖上述功能
```

### 5.1 提案 1：本地操作历史

**目标：** 记录每次会话的完整操作（命令输入 + 文件传输），按会话区分，支持审计和片段生成。

**核心难点：从交互式终端中区分「用户输入的命令」vs「交互式应用操作」。**

当前数据流（技术调研结论）：
- 用户输入路径：SwiftTerm → `TerminalCoordinator.sendToShell(_:)` → FFI `shellWrite` → Rust `ShellSession.write` → SSH channel
- 服务端输出路径：SSH channel → 内存 buffer → Swift 16ms 轮询 → `tv.feed(byteArray:)` 渲染
- **当前无任何命令解析或输入记录逻辑**，输入字节直接透传
- 最佳拦截点：`TerminalCoordinator.sendToShell(_:)`（Swift 侧统一入口）

**交互式应用的识别挑战：**

| 场景 | 识别难度 | 原因 |
|------|----------|------|
| 普通 shell 命令（`ls`, `cat`, `git status`） | 低 | 输入 = 命令，回车 = 执行边界 |
| vi / vim | 中 | 进入 vi 后所有按键都是编辑器操作，不是 shell 命令 |
| mysql / psql 等数据库客户端 | 中 | 有自己的一套 SQL 提示符和命令体系 |
| `ssh user@host`（嵌套 SSH） | 高 | 内层会话的命令属于另一台主机 |
| `su -` / `sudo -i`（切换用户） | 中 | 权限上下文变化，但仍是 shell 命令 |
| `tmux` / `screen`（终端复用器） | 高 | 内部窗口/面板的操作不是 shell 命令 |

**建议方案（分层记录）：**

1. **原始层（必须做）：** 记录所有输入/输出字节的带时间戳日志，按会话 ID 归档。这是审计的基础，不涉及任何解析。
2. **命令边界检测（核心难点）：** 基于输出流中的提示符模式（PS1/PS2）检测命令边界。大多数 shell 在命令执行完毕后会输出提示符（如 `$ `、`# `），可以通过正则匹配。当检测到以下模式时标记为「进入交互应用」：
   - 输入包含 `vi`、`vim`、`nano`、`mysql`、`psql`、`ssh`、`tmux`、`screen` 等关键词
   - 输出流不再出现 shell 提示符模式
3. **嵌套 SSH 处理：** 检测到 `ssh user@host` 命令时，标记当前会话进入「代理模式」，后续输入归属到目标主机的逻辑会话下。
4. **文件传输记录：** 已有 `TransferStore` 管理实时任务，需增加终态持久化（当前仅内存，重启丢失）。

**分阶段实施建议：**

| 阶段 | 内容 | 复杂度 |
|------|------|--------|
| P0 | 原始 I/O 日志（按会话 ID 归档，带时间戳） | 低 |
| P1 | 文件传输历史持久化 | 低 |
| P2 | 基于提示符模式的命令边界检测 | 中 |
| P3 | 交互应用模式识别（vi/mysql/ssh 等） | 高 |
| P4 | 嵌套 SSH 会话归属 | 高 |

**风险：** P2+ 的准确率取决于远程 shell 配置（自定义 PS1、zsh 主题、powerline 等），可能需要用户配置提示符模式或提供手动标注能力。

### 5.2 提案 2：代码片段深化

**目标：** 支持从终端选中文本加入片段、手动编辑、分类管理。

**当前状态（技术调研结论）：**
- Rust 侧 `Snippet` 已有：`name`、`title`、`tags: Vec<String>`、`body`（Markdown 正文）
- Swift 侧 `Snippet` 有：`id`、`title`、`tags: [String]`、`summary`、`code`（字段与 Rust 不完全对应）
- Swift 侧 `SnippetsView` 已实现：双栏布局、新建/编辑/删除、标签逗号分隔输入
- `SnippetStore` 支持：`list()`、`save()`、`delete()`，Markdown 文件存储

**需要新增的能力：**

| 能力 | 描述 | 依赖 |
|------|------|------|
| **终端选文 → 片段** | 在终端中选中文本 → 右键「加入代码片段」→ 自动填充代码区 | 操作历史（至少需要终端文本选择能力） |
| **分类/分组** | 片段按文件夹或标签层级组织，而非扁平列表 | 无 |
| **手动编辑器增强** | 语法高亮、行号、更好的代码编辑体验 | 无 |
| **片段搜索** | 在片段库中搜索标题、标签、代码内容 | 无 |
| **片段模板** | 参数化模板（如 `deploy-{env}`），执行时填入参数 | 操作历史 + 批量执行 |

**终端选文 → 片段的实现路径：**
- SwiftTerm 已支持文本选择（`tv.selectedText`）
- 需要在终端右键菜单增加「加入代码片段」选项
- 弹出片段创建 sheet，预填选中代码，用户补充标题/标签/说明

**建议优先级：** 分类/分组 > 终端选文 → 片段 > 搜索 > 编辑器增强 > 模板

### 5.3 提案 3：远程命令批量执行

**目标：** 按主机记录历史，多台主机并行执行同一命令。

**当前状态：** 无批量执行基础设施。

**核心设计问题：**

| 问题 | 建议 |
|------|------|
| 命令来源 | 手动输入 / 从操作历史选取 / 从代码片段选取 |
| 目标选择 | 从主机列表多选 / 从分组选择 / 从当前打开的标签页 |
| 执行方式 | 通过 `SshSession::exec_command`（已有，非交互式单命令执行） |
| 并行策略 | 各主机独立 SSH 连接，并行执行，各自收集 stdout/stderr/exit_code |
| 结果展示 | 按主机分栏展示输出，高亮差异，汇总退出码 |
| 超时控制 | 复用已有 60s 命令超时，支持用户自定义 |
| 安全约束 | 执行前展示将要执行的命令和目标主机列表，用户确认 |

**与操作历史的关系：**
- 操作历史按主机分开记录 → 用户可以从历史中选取命令 → 批量执行到其他主机
- 代码片段作为「已验证的可复用命令」→ 直接批量执行

**实施路径：**

| 阶段 | 内容 | 依赖 |
|------|------|------|
| P0 | 手动输入命令 + 多选主机 + 并行执行 + 结果汇总 | 无（exec_command 已有） |
| P1 | 从代码片段选取命令执行 | 代码片段深化 |
| P2 | 从操作历史选取命令执行 | 操作历史 P2+ |
| P3 | 执行计划预览（dry-run）+ 条件执行 | 中远期 |

### 5.4 提案 4：SSH 跳板机（Proxy Jump）

**目标：** 通过 SSH 代理主机 A 访问内网主机 B（B 不可直达）。

**当前状态（技术调研结论）：**
- `SshSession::connect` 直接 `TcpStream::connect((host, port))`，无任何代理逻辑
- `HostConfig` 字段：`id, name, host, port, username, auth, notes, group_id` — **无 proxy/jump 字段**
- 全仓无任何 proxy/jump/bastion 相关代码
- **russh 原生支持 `channel_open_direct_tcpip`**：通过已认证 SSH 连接打开 TCP 通道，返回的 Channel 实现 `AsyncRead + AsyncWrite`
- 当前 `connect` 已使用 `connect_stream`（而非 `connect(addr)`），替换流来源侵入性很小

**核心 SSH 改动（两种方案共享）：**
- `CountingStream` 当前硬编码 `inner: TcpStream`，需泛型化或 enum 化以同时支持 `TcpStream` 和 `ChannelStream`
- 连接流程：先建立跳板机 SSH → `handle.channel_open_direct_tcpip(target_host, target_port, ...)` → `Channel.into_stream()` → 传给 `client::connect_stream`
- `SshSession` 需持有跳板机 `Arc<SshSession>` 管理生命周期

#### 方案 A：引用已有 HostConfig id

```toml
# HostConfig 增加字段
proxy_jump = "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"  # 指向另一 HostConfig 的 id
```

| 维度 | 评估 |
|------|------|
| **数据模型** | `HostConfig` 增加 `proxy_jump: Option<String>`，改动最小 |
| **凭据处理** | 完全复用现有体系，跳板机凭据引用名沿用 `host.{id}.password` 约定 |
| **多级跳板** | 天然支持（递归引用：C.proxy_jump → B.proxy_jump → A） |
| **独立测试** | 跳板机本身是普通主机，可独立连接测试 |
| **UI** | 下拉选择已有主机，简单直观 |
| **劣势** | 跳板机必须在主机列表中存在；删除跳板机需检查引用 |
| **改动范围** | config.rs + ssh.rs + ffi + UI（中等） |

#### 方案 B：内嵌独立代理配置

```toml
# 新增 ProxyConfig 结构体
[host.proxy]
host = "bastion.example.com"
port = 22
username = "admin"
auth = { type = "public_key", key_path = "/keys/bastion_key" }
```

| 维度 | 评估 |
|------|------|
| **数据模型** | 新增 `ProxyConfig` 结构体，`HostConfig` 增加 `proxy: Option<ProxyConfig>` |
| **凭据处理** | 需新建代理凭据引用约定（如 `host.{id}.proxy.password`），CredentialStore 需扩展 |
| **多级跳板** | 需嵌套结构或限制单级，扩展性差 |
| **独立测试** | 代理配置无法独立连接测试 |
| **UI** | 需新建独立的代理配置表单 |
| **优势** | 配置自包含，导出/导入简单；删除主机无引用清理问题 |
| **改动范围** | 新增结构体 + 凭据约定 + ssh.rs + ffi + UI（较大） |

#### 方案对比结论

| 维度 | 方案 A（引用 id） | 方案 B（内嵌配置） |
|------|:-:|:-:|
| 改动范围 | 中 | 大 |
| 凭据复用 | 完全复用 | 需新建管理 |
| 多级跳板 | 天然递归 | 需嵌套或限制 |
| 独立测试 | 支持 | 不支持 |
| 配置自包含 | 否（依赖外部主机） | 是 |
| 删除安全 | 需检查引用 | 无引用 |

### 5.7 多级标签系统调研（代码片段分类）

> 2026-09-09 #4 调研完成。

#### 需求回顾

- 一个片段可挂多个标签，标签本身有层级（如 `网络/内核参数`、`故障处理/生产事故`）
- 跨场景归类：同一片段可同时属于不同维度的标签路径
- 支持按层级浏览和按标签搜索

#### 当前状态

`Snippet.tags` 已是 `Vec<String>`，存储在 Markdown frontmatter `tags: [deploy, git]` 中。标签为平级字符串，无层级关系。

#### 三个候选方案

**方案 A：路径字符串 + `/` 分隔（推荐）**

```yaml
# 片段 frontmatter
tags: ["网络/内核参数", "故障处理/生产事故", "性能优化/延迟调优"]
```

- 标签以 `"网络/内核参数"` 形式存储，与现有 `tags: Vec<String>` 完全兼容
- 约定 `/` 为层级分隔符，零迁移成本
- 独立 `tags.toml` 存储标签树（用于侧栏展示和自动补全），加载时从片段聚合初始化
- 查询：`starts_with("网络/")` 获取子树
- 与 Obsidian nested tags 同一思路，用户心智模型成熟

| 优势 | 劣势 |
|------|------|
| 零数据模型迁移 | 重命名父标签需批量更新子片段 |
| frontmatter 人类可读 | 不支持多父级（DAG） |
| 查询简单高效 | 标签名含 `/` 时有歧义（可约定转义） |
| `tags.toml` 仅做索引，丢失可重建 | — |

**方案 B：独立标签实体 + 关联 ID**

```toml
# tags.toml
[[tag]]
id = "tag-1"
parent_id = "tag-0"  # 根
name = "网络"

[[tag]]
id = "tag-2"
parent_id = "tag-1"
name = "内核参数"
```
```yaml
# 片段 frontmatter
tag_ids: ["tag-2", "tag-5"]
```

| 优势 | 劣势 |
|------|------|
| 重命名只改 tags.toml | frontmatter 存 ID 不可读 |
| 可支持 DAG（多 parent） | 片段与标签定义分离，需双向同步 |
| 结构最清晰 | 实现复杂度显著增加 |

**方案 C：纯 frontmatter 路径字符串，无独立标签文件**

与方案 A 相同存路径字符串，但不维护 `tags.toml`，每次从所有片段聚合出标签树。

| 优势 | 劣势 |
|------|------|
| 最简实现，无额外存储 | 片段量大时聚合慢 |
| — | 无法存标签元数据（描述、颜色） |
| — | 删除标签无显式操作 |

#### 方案对比

| 维度 | A（路径字符串 + 索引） | B（独立实体 + ID） | C（纯路径字符串） |
|------|:-:|:-:|:-:|
| 迁移成本 | 零 | 需迁移现有 tags | 零 |
| 人类可读 | 高 | 低（ID 不可读） | 高 |
| 查询效率 | 高 | 高 | 低（需聚合） |
| 重命名 | 批量替换 | 单点修改 | 批量替换 |
| 标签元数据 | 支持（tags.toml） | 支持 | 不支持 |
| 实现复杂度 | 低 | 高 | 最低 |
| DAG 支持 | 否 | 是 | 否 |

#### 推荐：方案 A

理由：
1. **与现有架构一致**：`tags: Vec<String>` 只需约定 `/` 分隔符，零迁移
2. **人类可读**：frontmatter 保持 `tags: ["网络/内核参数", "故障处理/生产事故"]`
3. **`tags.toml` 作为索引**：存储标签树结构，加载时从片段聚合初始化，后续增删标签同步更新。类似 `groups.toml` 模式
4. **查询高效**：按标签浏览 = 过滤 `tags.iter().any(|t| t.starts_with(prefix))`
5. **运维场景标签量有限**（数十到数百），批量替换性能无压力

#### UI 交互建议

| 场景 | 交互 |
|------|------|
| **侧栏浏览** | 树形展开（`DisclosureGroup`），与现有主机组侧栏一致 |
| **给片段打标签** | 输入框 + 自动补全（从 `tags.toml` 匹配），支持输入新路径即时创建 |
| **过滤逻辑** | 默认 OR（选中标签并集），可切换 AND（交集） |
| **标签管理** | 右键标签 → 重命名 / 删除（级联更新子标签和关联片段） |

#### 已确认

- 方案 A（路径字符串 + `tags.toml` 索引）— **已确认**
- 标签层级分隔符：`/` — **已确认**
- 过滤默认逻辑：OR（并集），可切换 AND — **已确认**

## 八、产品愿景（2026-09-09 #5 升级）

> 产品定位从「极简 SSH 客户端」升级为「AI 原生的远程运维智能平台」。

### 8.1 愿景声明

**Panda SSH 将成为 AI 时代具有明显特征的远程服务器管理工具。**

不是「SSH 客户端 + AI 附加功能」，而是从底层重新设计，让 AI 成为产品的核心能力而非装饰。

**核心特征：**
- **意图驱动** — 用户说目的，系统建议并执行命令
- **操作模式学习** — 从历史操作中发现规律，主动建议下一步
- **跨主机关联分析** — 自动发现多台主机之间的关联和异常
- **事故复盘** — 自动生成操作时间线，还原故障过程
- **风险预评估** — 执行前评估风险，基于历史结果预警
- **深度集成** — 容器集群排查、微服务故障诊断、日志分析

### 8.2 市场空白

竞品调研结论（2026-09-09）：

| 类型 | 代表产品 | 能力 | 局限 |
|------|----------|------|------|
| AIOps 平台 | Datadog / Dynatrace / PagerDuty | 监控 + 告警 + 根因分析 | 闭源 SaaS、价格高、只看不动 |
| AI 终端 | Warp 2.0 | 命令建议 + 输出解释 | 闭源、仅本地终端、不涉及远程管理 |
| K8s 工具 | K8sGPT / Lens Prism | 集群诊断 | 只管集群不管裸机 |
| 日志分析 | Elastic ML Streams | 自动日志解析 | 需完整 ELK 栈，偏可观测性非交互式运维 |
| SSH 客户端 | Termius / FinalShell / Xshell | 远程连接 + 文件传输 | 无 AI 能力或仅有实时监控 |

**空白地带：没有工具同时具备「直接 SSH 访问 + 深度 AI 分析 + 开源」三要素。**

- AIOps 平台「只看不动」——能分析但不能直接 SSH 操作
- 终端工具「能操作但 AI 浅」——Warp 的 AI 限于命令补全
- K8s 工具「只管集群不管裸机」——不涉及通用服务器管理
- SSH 客户端「能操作但无 AI」——传统工具没有智能分析能力

**Panda SSH 的差异化定位：直接服务器访问 × 深度 AI 分析 × 开源。**

### 8.7 巡检功能设计决策（2026-09-09 #6 确认）

#### 决策 1：巡检方案为独立功能实体

巡检方案**不是**代码片段的扩展类型，而是独立的功能实体，但可以在方案中引用代码片段。

**理由：** 巡检方案与代码片段有本质区别——巡检方案包含采集命令 + 解析规则 + 目标选择 + 阈值配置，是一个结构化的运维工作流定义；代码片段是纯文本的命令/脚本复用。

**巡检方案结构：**

```
InspectionProfile {
    id: String,
    name: String,                    // 如「日常巡检」「深度巡检」「磁盘专项」
    tags: Vec<String>,               // 多级标签，如「巡检/日常」「巡检/深度」
    description: String,
    items: Vec<InspectionItem>,      // 采集项列表
    target_rules: TargetRules,       // 目标选择规则
    thresholds: Vec<Threshold>,      // 阈值配置（可选）
}

InspectionItem {
    id: String,
    name: String,                    // 如「CPU 负载」「内存使用率」
    metric_key: String,              // 指标标识，如 cpu_load, mem_used_pct
    command_source: CommandSource,   // 命令来源
    parse_rule: ParseRule,           // 解析规则
    unit: String,                    // 单位（%, MB, GB, 次/秒等）
}

CommandSource = Inline(String)       // 内联命令
             | SnippetRef(String)    // 引用代码片段 id

ParseRule = Regex { pattern, groups } // 正则提取
          | JsonPath { path }        // JSON 路径提取
          | KeyValue { separator }   // KV 格式解析
```

**与代码片段的关系：**
- 简单命令 → 内联（`Inline("uptime")`）
- 复杂脚本 → 引用代码片段（`SnippetRef("snippet-id")`）
- 代码片段被引用时，其内容作为采集命令执行
- 代码片段更新后，所有引用它的巡检方案自动使用新内容

#### 决策 2：数据库选型 — SQLite + sqlite-vec

**调研结论（2026-09-09）：**

| 候选 | 结构化查询 | 向量搜索 | Rust 绑定 | Swift/iPadOS | 结论 |
|------|:-:|:-:|:-:|:-:|------|
| **SQLite + sqlite-vec** | 优 | 支持（扩展） | 成熟（rusqlite） | 原生支持 | **推荐** |
| DuckDB | 极优（列式分析） | 不支持 | 有 | 移动端未就绪 | 排除 |
| LanceDB | 支持 | 优 | 有 | 无 Swift 绑定 | 排除 |
| SurrealDB 嵌入 | 支持 | 支持 | 原生 Rust | 无 Swift 绑定 | 太年轻 |
| 纯 SQLite | 优 | 不支持 | 成熟 | 原生支持 | 备选 |

**推荐方案：SQLite 统一存储 + sqlite-vec 向量扩展**

- **一个数据库统一存储**：巡检快照、操作历史、批量执行结果、代码片段索引、向量 embeddings
- **sqlite-vec**：SQLite 官方认可的向量搜索扩展，同一数据库内做结构化查询 + 向量相似度搜索
- **数据量无压力**：数万到数十万条记录，SQLite 配合合理索引完全胜任
- **Rust/Swift 绑定成熟**：rusqlite 是 Rust 生态最成熟的 SQLite 绑定，iPadOS 原生支持 SQLite
- **未来扩展**：Phase 2-3 的命令历史语义搜索直接用 sqlite-vec 做 embedding 相似度查询，无需引入第二个数据库

**数据库文件规划：**

```
~/.panda-ssh/
├── hosts.toml              # 主机配置（保持现有）
├── groups.toml             # 分组配置（保持现有）
├── tags.toml               # 标签索引（保持现有）
├── snippets/               # 代码片段 Markdown 文件（保持现有）
├── panda.db                # 新增：统一数据数据库
│   ├── inspection_profiles # 巡检方案定义
│   ├── inspection_snapshots # 巡检快照（时序指标）
│   ├── operation_history   # 操作历史
│   ├── batch_results       # 批量执行结果
│   ├── transfer_history    # 文件传输历史
│   └── vector_embeddings   # 向量 embeddings（sqlite-vec）
└── credentials.toml        # 凭据存储（保持现有）
```

#### 概念模型

#### MCP Tools vs Skills 的关系

| 维度 | MCP Tools | Skills |
|------|-----------|--------|
| **粒度** | 原子操作 | 多步编排 |

#### Skill 定义格式（草案）

```yaml
# 巡检方案就是一个 Skill
name: 日常巡检
tags: ["巡检/日常", "生产环境"]
description: 对生产环境主机执行常规健康检查

# Skill 可以引用的 MCP Tools 来源
mcp_servers:
  - builtin  # Panda SSH 内置的 SSH/SFTP tools

# Skill 的输入参数
inputs:
  - name: target
    type: string
    description: 目标主机分组或标签
    default: "env/prod"

# Skill 的执行步骤
steps:
  - name: 采集指标
    tool: batch_exec
    input:
      host_ids: "{{resolve_hosts(target)}}"
      command: "uptime && free -m && df -h && cat /proc/net/dev"
    output: raw_results

  - name: 解析结果
    action: parse_metrics
    input:
      data: "{{raw_results}}"
      rules:
        - metric: cpu_load
          pattern: "load average: (\\d+\\.\\d+)"
        - metric: mem_used_pct
          pattern: "Mem:.*?(\\d+).*?(\\d+)"
          expression: "$2 / $1 * 100"
        - metric: disk_used_pct
          pattern: "/dev/.*?(\\d+)%"

  - name: 存储快照
    action: store_snapshot
    input:
      profile_id: "{{this.id}}"
      metrics: "{{parsed_metrics}}"

  - name: 阈值检查
    action: check_thresholds
    input:
      metrics: "{{parsed_metrics}}"
      thresholds:
        - metric: cpu_load
          operator: ">"
          value: 80
          severity: warning
        - metric: disk_used_pct
          operator: ">"
          value: 85
          severity: critical

  - name: 生成报告
    action: render_report
    template: inspection_report.html
    output: report_html
```

#### 对能力架构的影响

原来的五层同心圆模型需要调整——**MCP + Skills 不是最外层的生态扩展，而是贯穿各层的核心机制**：

```
旧模型：                          新模型：
┌──────────────┐                 ┌──────────────────────┐
│ 4.生态扩展    │                 │   AI Agent 层         │
├──────────────┤                 │  (编排 Skills)        │
│ 3.AI 分析     │                 ├──────────────────────┤
├──────────────┤                 │   Skills 层           │
│ 2.本地智能    │                 │  (巡检/部署/排查...)   │
├──────────────┤                 ├──────────────────────┤
│ 1.数据基础    │                 │   MCP 协议层          │
├──────────────┤                 │  (内置 + 外部 Tools)  │
│ 0.核心层      │                 ├──────────────────────┤
└──────────────┘                 │   数据 + 核心层       │
                                 └──────────────────────┘
```

**MCP + Skills 是中间层，向上为 AI 提供编排能力，向下为数据/核心层提供扩展入口。**

#### 对演进路线的影响

| Phase | 原计划 | 调整后 |
|-------|--------|--------|
| Phase 0 | 跳板机 + 代码片段 | 不变 |
| Phase 1 | 操作历史 + 批量执行 + 巡检 | + **MCP Server 基础版**（暴露 SSH/SFTP 为 MCP Tools） |
| Phase 2 | 本地智能 + 巡检对比 | + **Skill 引擎**（支持 Skill 定义、执行、步骤编排） |
| Phase 3 | AI 分析 | + **AI Agent 层**（编排 Skills + 调用 MCP Tools） |
| Phase 4 | 生态扩展 | + **外部 MCP Server 集成**（K8s/ES/Docker）+ **社区 Skill 共享** |

**关键变化：MCP Server 提前到 Phase 1。** 理由：
1. Rust MCP SDK 已成熟（官方 rust-sdk + rmcp）
2. 暴露 SSH/SFTP 为 MCP Tools 的改动不大（核心能力已有，只需加一层 MCP 协议封装）
3. 尽早让外部 AI Agent 能调用 Panda SSH 能力，建立生态位

#### AI 模型策略（已决）

**同时支持本地模型和云端 API Key，用户可选择：**

| 模式 | 适用场景 | 隐私 |
|------|----------|------|
| **本地模型** | 命令建议、输出解析、模式识别 | 完全本地，零泄露 |
| **用户自带 API Key** | 复杂推理、报告生成、跨主机关联 | 用户控制，数据发送到用户选择的 provider |
| **混合模式** | 简单任务用本地，复杂任务用云端 | 分级处理 |

**实现方式：**
- 设置页提供 AI 模型配置：本地模型路径 / API Key + endpoint
- 每个 Skill 可配置所需 AI 能力级别（无需 AI / 建议本地 / 需要云端）
- 敏感操作（涉及终端输出）默认使用本地模型

### 2026-09-09 #10 — Skill 开源标准调研

**背景：** 用户要求调研 Skill 方面的开源标准，社区共建暂缓。

### 2026-09-09 #9 — 场景化产品设计

**背景：** 用户要求从互联网抓取 20+ SSH 业务场景，基于场景进行产品设计。

1. 最高频场景（日常）集中在 L0+L1 能力层——巡检、日志、服务管理

3. **周期性场景最适合自动化**：合规检查、密钥审计、批量补丁——重复性高，Skill + 定时触发 = 巨大效率提升
4. **跨主机关联是 AI 的核心价值**：#6 性能诊断、#10 应急响应、#18 K8s 排查——都需要在多台主机间交叉对比，这正是 AI 擅长的
5. **端口转发是基础能力缺口**：#15 #16 #17 三个场景都需要，应提升到 Phase 0

## 十一、Skill 开源标准调研（2026-09-09 #10）

> 用户决策：Skill 格式遵循开源标准。本章调研当前生态中的 Skill/Tool 定义标准，为 Panda SSH 的 Skill 系统设计提供依据。

### 11.1 生态现状：两种互补的抽象

当前 AI Agent 生态中存在两种互补的抽象层：

| 抽象 | 定义 | 代表 | 特点 |
|------|------|------|------|
| **Tool（原子能力）** | 声明式：我能为 AI 提供什么操作 | MCP Tools、OpenAI Function Calling | JSON Schema 描述输入输出，无状态，AI 决定何时调用 |
| **Skill（编排流程）** | 指令式：告诉 AI 如何完成一个任务 | CrewAI SKILL.md、Semantic Kernel Plugin | 多步骤编排，有状态，可包含业务逻辑和验证规则 |

**关键关系：Skill 编排 Tools。** Skill 在执行过程中调用 Tools 完成具体步骤，验证输出，再决定下一步。

### 11.2 各框架 Skill/Tool 定义格式

#### MCP Tools（事实标准）

```json
{
  "name": "ssh_exec",
  "description": "在已连接的 SSH 会话上执行命令",
  "inputSchema": {
    "type": "object",
    "properties": {
      "connection_id": { "type": "string", "description": "连接标识" },
      "command": { "type": "string", "description": "要执行的命令" },
      "timeout": { "type": "number", "description": "超时秒数", "default": 60 }
    },
    "required": ["connection_id", "command"]
  }
}
```

- **规范版本**：2025-06-18（稳定），2026-07-28（RC）
- **发现机制**：客户端发送 `tools/list`，服务端返回工具列表
- **传输层**：stdio（本地进程）或 Streamable HTTP（远程服务）
- **生态支持**：Anthropic、OpenAI、Microsoft、Google 均已支持或桥接

#### CrewAI SKILL.md（指令式 Skill）

```markdown
---
name: 日常巡检
description: 对生产环境主机执行常规健康检查
license: Apache-2.0
compatibility: panda-ssh >= 1.0
allowed-tools:
  - ssh_exec
  - batch_exec
  - sftp_download
---

# 日常巡检

## 步骤

1. 解析目标参数，确定主机列表
2. 对每台主机执行以下采集命令：
   - `uptime` → 提取 CPU 负载
   - `free -m` → 提取内存使用率
   - `df -h` → 提取磁盘使用率
   - `cat /proc/net/dev` → 提取网络流量
3. 将结果解析为结构化指标
4. 与阈值对比，标记告警项
5. 生成巡检报告（HTML 格式）

## 阈值

| 指标 | 告警 | 严重 |
|------|------|------|
| CPU 负载 | > 80% | > 95% |
| 内存使用率 | > 85% | > 95% |
| 磁盘使用率 | > 85% | > 95% |
```

- **格式**：Markdown + YAML frontmatter + 子目录（scripts/、references/、assets/）
- **注册**：`crewai skill publish` 到中心 registry
- **特点**：人类可读，AI 可理解执行意图，适合复杂运维流程

#### YAML 声明式工作流（GitHub Actions 风格）

```yaml
name: 滚动部署
on:
  trigger: manual
  input:
    - name: service
      type: string
    - name: version
      type: string
    - name: target_group
      type: string
      default: "env/prod"

steps:
  - name: 解析目标主机
    action: resolve_hosts
    input:
      selector: "{{target_group}}"
    output: hosts

  - name: 逐节点部署
    strategy: rolling
    batch_size: 1
    input:
      hosts: "{{hosts}}"
    steps:
      - name: 拉取新版本
        tool: ssh_exec
        input:
          command: "cd /app && git pull origin {{version}}"
      - name: 重启服务
        tool: ssh_exec
        input:
          command: "systemctl restart {{service}}"
      - name: 健康检查
        tool: ssh_exec
        input:
          command: "curl -sf http://localhost/health"
        retry:
          max_attempts: 3
          backoff: 5s

  - name: 验证部署
    tool: batch_exec
    input:
      host_ids: "{{hosts}}"
      command: "curl -sf http://localhost/version | grep '{{version}}'"
```

- **特点**：确定性执行，不依赖 LLM 规划，适合关键流程
- **参考**：GitHub Actions、Argo Workflows、Kestra

### 11.3 互操作性分析

| 框架 | MCP 兼容 | Skill 格式 | 工作流定义 |
|------|:--------:|-----------|-----------|
| MCP 原生 | — | — | — |
| OpenAI | 桥接 | function calling | — |
| Semantic Kernel | 原生导入 | Plugin（代码注解） | — |
| CrewAI | 桥接 | SKILL.md | — |
| LangChain | 桥接 | 代码类 | — |
| GitHub Actions | — | — | YAML |
| Argo Workflows | — | — | YAML |

**结论：MCP 是 Tool 层的互操作标准，但 Skill/Workflow 层尚无统一标准。**

### 11.4 推荐方案：三层 Skill 架构

```
┌──────────────────────────────────────────────────┐
│  Skill 定义层（SKILL.md 格式）                    │
│  人类可读的 Markdown + YAML frontmatter           │
│  定义意图、步骤、阈值、模板                        │
├──────────────────────────────────────────────────┤
│  工作流引擎层（Rust 核心）                        │
│  解析 Skill 定义，编排执行步骤                     │
│  支持确定性执行 + AI 辅助决策的混合模式            │
├──────────────────────────────────────────────────┤
│  Tool 能力层（MCP 协议）                          │
│  内置 MCP Tools：ssh_exec, batch_exec, sftp_*     │
│  外部 MCP Servers：K8s, ES, Docker...            │
└──────────────────────────────────────────────────┘
```

**设计原则：**

1. **Skill 定义用 SKILL.md 格式**（Markdown + YAML frontmatter）
   - 人类可读可编辑（Markdown 正文描述意图和步骤）
   - 机器可解析（YAML frontmatter 声明参数、工具依赖、阈值）
   - 与 CrewAI 生态兼容（格式对齐，可互相借鉴社区 Skill）
   - 文件存储在 `~/.panda-ssh/skills/` 目录，每个 Skill 一个子目录

2. **Tool 能力用 MCP 协议**
   - 内置 MCP Server 暴露 SSH/SFTP/批量执行等原子操作
   - 外部 MCP Server 扩展 K8s/ES/Docker 等能力
   - JSON Schema 描述输入输出，标准发现机制

3. **工作流引擎在 Rust 核心**
   - 解析 SKILL.md → 构建执行计划
   - 支持两种执行模式：
     - **确定性模式**：按步骤严格执行（适合关键流程如部署、主从切换）
     - **AI 辅助模式**：LLM 根据 Skill 描述和当前上下文动态决策（适合诊断、排查）
   - 步骤间上下文传递（前一步输出可作为后一步输入）
   - 错误处理：retry + onFailure + 回滚

**演进路线调整：**

### 2026-09-09 #6 — 巡检功能设计决策

**背景：** 用户对巡检功能三个设计问题给出决策。

**决策确认：**
1. **巡检方案独立**：不是代码片段的扩展类型，而是独立功能实体。可在方案中引用代码片段（`SnippetRef`）。巡检方案 = 采集命令 + 解析规则 + 目标选择 + 阈值配置。
2. **数据库选型**：SQLite + sqlite-vec。调研了 DuckDB（移动端未就绪）、LanceDB（无 Swift 绑定）、SurrealDB（太年轻），SQLite 在数据量、绑定成熟度、iPadOS 兼容性上全面胜出。sqlite-vec 扩展支持向量搜索，为 Phase 2-3 的语义搜索做准备。
3. **报告格式**：应用内查看 + HTML 导出。不采用 PDF（静态格式，不支持交互）。HTML 可通过模板实现动态效果。

**新增数据模型设计：**
- `InspectionProfile`：方案定义（名称、标签、采集项、目标规则、阈值）
- `InspectionItem`：采集项（指标名、命令来源、解析规则、单位）
- `CommandSource`：内联命令或代码片段引用
- `ParseRule`：正则 / JSON 路径 / KV 格式

**数据库文件规划：** `~/.panda-ssh/panda.db` 统一存储巡检快照、操作历史、批量结果、传输历史、向量 embeddings。
