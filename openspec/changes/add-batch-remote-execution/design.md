# 设计：远程命令批量执行（add-batch-remote-execution）

## Context

现有原语与约束（详见 proposal.md Why 与路线图 5.3/8.6）：

- `crates/panda-core/src/ssh.rs`：`SshSession::exec` / `exec_with_timeout`（默认 60 秒超时），返回 `ExecOutput { stdout, stderr, exit_status: Option<u32> }`——退出码是 `Option`，天然承载「未收到退出码」这一事实。
- 每次连接请求新建一条 `SshSession`，所有者独占（`ssh-connection`、`connection-pool` 规格）；活动连接注册表可承载运行时查找与遥测。
- panda-ffi 全部同步导出，异步跑在懒初始化的全局 tokio runtime（`block_on`）；路线图 8.6「长任务」要求：同步 FFI 返回简单任务标识/状态，异步执行留在既有全局 runtime。
- fake SSH 测试基础：`crates/panda-ffi/tests/ffi_fake_server.rs`（russh 内存服务器，`exec_request` 目前固定回 0）。
- UI 参照模式：`apple/PandaSSH/Workspace/TransferStore.swift`（任务六态 + version 增量轮询）与 `TransferPanelView.swift`（全局任务面板，关闭页面不影响任务生命周期）。
- 依赖契约：授权（add-execution-plan-authorization：计划结构、审批状态、执行前强制检查）、审计（add-command-audit-trail：记录与阻断语义）、重连语义边界（improve-connection-reliability：重连不自动重发）。这些提案并行生成中，本提案通过 trait 端口消费其契约，落点以其归档规格为准。

## Goals / Non-Goals

**Goals:**

- 定义 `batch_exec` 模块内部架构：计划展开 → 授权校验 → 有界调度 → 状态持久化 → 恢复核对的流水线与 trait 边界。
- 给出九态状态机的状态迁移表与终态判定规则（未收到退出码永不默认成功）。
- 给出资源预算的具体默认值与可配置边界（规格只约束「必须有界且可审核」，数值在此定）。
- 定义 FFI 面（同步导出、任务标识、增量轮询）与 Swift 任务窗口的接入方式。
- 定义 fake SSH / fake 时钟 / fake 存储的测试基座形态，支撑 TDD。

**Non-Goals:**

- 不实现定时调度（macOS 定时、iPadOS 定时均不在范围）。
- 不实现 MCP 入口、多维标签选择、滚动部署编排。
- 不选择 SQLite 等结构化存储（沿用路线图 8.6：数据选型由后续数据层提案统一，本提案先用文件持久化满足可恢复性）。
- 不实现通用回滚或跨主机事务。

## Decisions

### D1：模块与依赖边界——全部业务逻辑落 `crates/panda-core`，四个 trait 隔离外部世界

新增 `crates/panda-core/src/batch_exec.rs`（内部可再拆子模块），对四个外部依赖定义 trait，生产实现与 fake 实现分离：

| Trait | 职责 | 生产实现 | fake 实现 |
|---|---|---|---|
| `ExecTransport` | 按计划（主机、凭据引用、跳板链）建立任务独占连接并执行单命令，返回 `ExecOutput` 与断线/超时分类 | 包一层 `SshSession`（复用 `exec_with_timeout`） | 内存脚本化执行器 |
| `TaskClock` | 单步等待、总预算、时间戳 | `std::time` / tokio 时钟 | 手动拨动的假时钟 |
| `TaskStateStore` | 任务与逐主机状态/结果的原子持久化与读取 | `<config_dir>/batch-tasks/<task_id>/` 下 JSON 文件（tmp+rename 原子写） | 内存 HashMap |
| `AuditSink` | 消费共享审计契约端口（与 add-execution-plan-authorization design D6 定义的 `AuditSink` 为同一 trait，生产实现由 add-command-audit-trail 交付，本提案不重复定义）：写入计划/批准/尝试/结果关联记录，暴露审计健康状态 | 对接审计提案的落点 | 内存记录器，可注入写入失败 |

备选方案：把调度器放在 panda-ffi 或 Swift——被否决，违反「业务逻辑只落 panda-core」与双端一致性；直接依赖 russh 而不经 trait——被否决，无法用 fake 做「断线/慢命令」等 TDD 场景，也无法对接未来的授权/审计契约替身。

### D2：九态状态机与迁移表

逐主机步骤状态（任务级状态由逐主机状态派生，规则见下）：

| 当前态 | 事件 | 次态 |
|---|---|---|
| 排队 | 计划生成并提交、未批准 | 等待批准 |
| 等待批准 | 批准生效 + 授权检查通过 | 排队（进入可派发队列） |
| 排队 | 并发额度可用 + 派发前检查（授权、审计健康、预算）通过 | 运行 |
| 排队 | 计划被拒/撤销/过期 | 已确认停止（未派发，无远端副作用） |
| 运行 | 收到退出码 0 | 成功 |
| 运行 | 收到非零退出码 | 失败 |
| 运行 | 单步等待超时（停止等待） | 超时 |
| 运行 | 连接断开且无退出码 | 结果未知 |
| 运行/超时/排队 | 用户停止 | 取消请求 |
| 取消请求 | 通道关闭/会话释放获确认（或本就未派发） | 已确认停止 |
| 取消请求 | 无法确认远端已终止 | 结果未知 |
| 超时/结果未知 | 重入核对客观确认（验证步骤通过/明确失败） | 成功 / 失败（验证结论另记于独立验证结论字段：目标完成/目标未完成，不作为执行状态） |
| 超时/结果未知 | 总预算耗尽且无法核对 | 结果未知（保持可见） |

任务级派生规则：全部目标主机达到终态且执行状态均为「成功」、验证结论均为「目标完成」（无验证步骤视同通过）→ 任务成功；存在任一「结果未知/超时」→ 任务呈现「部分完成·含未决」，MUST NOT 出现整体成功结论；其余按失败/取消计数呈现。终态不可逆（除结果未知经重入核改判一次并留痕）。

备选：只用「成功/失败/其他」三态——被否决，无法承载审计可区分记录与「停止等待≠远端已停止」语义。

### D3：有界资源的具体默认值与可配置边界

全部预算进入执行计划、随计划一并审核；运行期不可被任务自身修改。默认值：

| 预算 | 默认值 | 可配边界 |
|---|---|---|
| 主机并发 | 4 | 1..=16 |
| 每主机步骤并发 | 1 | 1..=4（串行是默认安全语义） |
| 单步等待时间 | 60 秒（与 `EXEC_TIMEOUT` 语义一致） | 1..=3600 秒 |
| 每路输出上限（stdout/stderr 各自） | 1 MiB（超出截断并标记「已截断」） | 64 KiB..=16 MiB |
| 任务总时长 | 30 分钟 | 1 分钟..=24 小时 |
| 任务总输出 | 64 MiB | 每路输出上限..=512 MiB |
| 重试预算（仅限未派发失败） | 0（默认不自动重试） | 0..=2 |
| 目标主机数上限 | 100（超过须拆分计划） | 固定上限，防误操作全选分组 |

背压策略：不设独立丢弃队列——超出并发上限的步骤一律停留在「排队」，按「提交顺序 + 主机轮转」获得额度；总预算耗尽时调度器停止派发，剩余排队步骤记为可区分的「未执行（预算耗尽）」终态。备选：动态调节并发（按负载伸缩）——被否决，首版追求可预测与可审核。

### D4：断线/超时分类与「永不默认成功」

`ExecOutput.exit_status` 为 `None`、执行通道 EOF/读写错误、或 `exec_with_timeout` 返回 `Timeout` 时，按以下映射：

- `Timeout`（等待超上限，客户端主动停止等待）→ 步骤「超时」，提示远端可能仍在运行；
- 连接断开且已派发、退出码缺失 → 「结果未知」（无论是否已收集到部分输出）；
- 连接建立失败/认证失败（命令未派发）→ 「失败（未派发）」，是唯一允许自动重试的类别（受 D3 重试预算约束）。

任何「成功」判定必须以收到的退出码 0 为前提；「目标完成」还须验证步骤通过。

### D5：崩溃恢复与重入核对

每次状态迁移即原子写持久化（D1 `TaskStateStore`），崩溃丢失窗口为单次迁移。重启后：终态保留；「运行/取消请求/超时」未决步骤改记「结果未知（待核对）」。恢复流程：用户对未决主机发起重入核对 → 系统执行计划中的验证步骤（或计划声明的核对命令）→ 验证客观通过则改判「成功/目标未完成」，客观失败则改判「失败」，无法判定则保持「结果未知」。不自动恢复执行：剩余排队步骤的续跑由用户显式确认后进行（经执行前检查），重连本身不触发重发（对齐 improve-connection-reliability 边界）。

### D6：FFI 面——同步导出 + 简单任务标识 + version 增量轮询

新增同步导出（uniffi，简单值类型 Record/Enum）：

- `batch_exec_submit(plan) -> taskId`：校验并持久化任务（初始态「等待批准」），返回简单任务 ID 字符串；异步执行体 spawn 到既有全局 tokio runtime，`block_on` 仅用于启动与查询，不等待执行完成。
- `batch_exec_status(taskId, sinceVersion) -> (version, taskSummary, hostStates[])`：增量轮询，version 单调递增（沿用 TransferStore 模式）。
- `batch_exec_stop(taskId)` / `batch_exec_resume(taskId, hostIds)` / `batch_exec_reconcile(taskId, hostIds)`：停止、显式恢复、重入核对。
- `batch_exec_list() -> [taskId]`：供任务窗口列出历史任务。

备选：流式回调推送状态——被否决，uniffi 同步契约与双端轮询模式已验证（传输面板），复杂度不值得。

### D7：Swift 任务窗口

工作区新增任务入口（与传输面板同级），`BatchTaskStore`（ObservableObject）轮询 `batch_exec_status` 增量版本；任务列表 → 任务详情（逐主机九态徽标、输出查看、停止/恢复/核对按钮）。复用传输面板「关闭页面不影响任务生命周期」的持有方式（store 由应用级持有）。双端共享源码；无业务级 `#if os()`（仅窗口呈现与后台提示按平台服务差异处理）。iPadOS 不提供任何定时入口；App 切后台后任务状态以持久化为准，回前台按 D5 处理。

### D8：测试基座

- core 层：`ExecTransport`/`TaskClock`/`TaskStateStore`/`AuditSink` 的 fake 直接注入调度器单测，覆盖正常/意外/边界三类（慢命令、断连、超限、预算耗尽、并发上限、审计失败）。
- FFI 层：扩展 `ffi_fake_server.rs` 的 `exec_request` 支持脚本化行为表（按命令前缀返回指定退出码、延迟、输出量、中途断连），跑端到端 fake 场景。
- Swift 层：`BatchTaskStore` 状态映射与徽标文案用 XCTest；纯布局不测。

### D9：凭据与审计的消费方式

- 凭据：计划仅含凭据引用（`*_ref`）+ 连接层按授权使用；任务引擎不读取、不落盘凭据材料，Swift 从钥匙串取出后作为连接参数传入（现有 FFI 约定）。凭据存储基线冲突由 resolve-baseline-conflicts 消解，本提案不复述「只存钥匙串」为既定事实。
- 审计：调度器每次派发前查询 `AuditSink` 健康状态；写入失败或完整性核验失败 → 阻断派发新步骤（规格「审计阻断」），已发出步骤结果仍如实记录并标注审计缺失。

## Risks / Trade-offs

- [SSH 无通用「杀远端进程」手段，停止等待后远端可能继续运行] → 状态语义上不声称远端已停止（「取消请求→已确认停止」仅在通道关闭获确认后）；输出呈现明确提示；文档建议远端命令自行幂等/限时。
- [崩溃恢复窗口内输出丢失] → 每次迁移即原子写；丢失部分表现为「结果未知」，宁可未知不误报。
- [iPadOS 后台挂起中断执行] → 持久化 + 回前台重入核对；UI 明示平台限制，不承诺后台完成。
- [轮询延迟与电量（尤其 iPadOS）] → version 增量使空轮询廉价；运行期轮询间隔与任务活动性挂钩（设计常量，UI 可再调）。
- [依赖提案并行生成中，契约细节可能漂移] → 以 D1 的 trait 端口隔离；评审阶段对齐字段命名与审计记录格式；本提案 spec 只引用行为契约不引用具体类型。
- [分组展开依赖 groups.toml 当前定义，用户先建计划后改分组] → 展开结果固化为具体主机 ID 并随计划版本审核，分组后续变化不影响已批准计划（但主机密钥异常仍使授权失效）。

## Migration Plan

1. 纯新增：新模块 + 新 FFI 函数 + 新任务窗口，不改既有路径行为；旧版本配置文件无需迁移。
2. 依赖就绪顺序：授权提案先归档（强制检查入口可用），审计提案可稍后（`AuditSink` 先接内存/文件桩，审计归档后切生产实现）。
3. 回滚：功能入口随 UI 开关移除即可；任务目录数据独立，残留不影响其他能力。

## Open Questions

- 输出超过内存友好阈值时的落盘形态（内联 JSON vs 独立输出文件）：不影响规格行为与任务拆解，实现任务内定。
- 片段「内容版本标识」的具体格式：随 deepen-snippet-system / 审计提案归档对齐，本提案仅消费「可标识版本」这一契约。
- 灰度批次（分批派发目标子集）的批次默认大小与 UI 呈现：列为后续任务组，批次上限沿用 D3 目标主机数上限，默认值实现时定。
- 条件步骤（前序成功才执行）的表达语法：后续任务组内设计，不影响本批 spec。
