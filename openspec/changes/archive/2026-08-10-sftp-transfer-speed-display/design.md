## Context

`TransferStore` 已经管理 `TransferTask` 列表，每个任务包含 `size`、`transferred`、`status` 等状态，并通过轮询 Rust FFI 的 `poll_transfer` 更新进度。当前 UI 只展示进度百分比与已传/总字节数，未利用这些进度点的时间信息。

## Goals / Non-Goals

**Goals:**
- 在传输面板为每个任务展示实时速度、总速度与剩余时间。
- 速度计算逻辑可测试，且不依赖真实网络或真实 SSH 服务器。
- macOS 与 iPadOS 共享同一套 ViewModel / 计算逻辑。

**Non-Goals:**
- 不修改 Rust `panda-core` 或 `panda-ffi` 的传输接口。
- 不做全局带宽限制、历史记录持久化或详细网络诊断。
- 不针对 Mock 模式做专门的速度模拟。

## Decisions

### 1. Swift 侧基于进度时间戳计算速度

**选择：** 在 Swift ViewModel 中维护每个任务的进度历史（时间戳 + 已传字节），由 Swift 推导速度。

**理由：**
- Rust 侧当前进度回调/轮询已经提供 `transferred` 字节数；Swift 端轮询本身就会记录更新时间。
- 不增加 FFI 复杂度，也避免跨语言传输高频速度数据。
- 未来若需更精确的瞬时速度，再考虑在 Rust 侧按固定时间间隔上报也不迟。

**替代方案：** 在 Rust `panda-core` 的 `SftpClient` 上传/下载回调里直接计算速度并通过 FFI 暴露。此方案更精确，但会增加 FFI 与核心库的改动量，本期先保持最小侵入。

### 2. 滑动窗口计算实时速度

**选择：** 使用 2 秒滑动窗口，窗口内保留 `(timestamp, bytes)` 数据点；实时速度 = 窗口内首尾两点字节差 / 时间差。

**理由：**
- 2 秒在人类可感知范围内足够平滑，又不会让速度显示过于滞后。
- 首尾两点法实现简单、可测试，避免复杂回归或滤波。

**边界：** 窗口内只有单个数据点时，退化到与起始点计算；没有数据点时速度为 0。

### 3. 总速度基于任务开始时间

**选择：** 总速度 = `transferred / (now - startTime)`；任务开始时间取任务入队或首次收到进度的时间。

**理由：**
- 符合用户感知的"从开始到现在平均有多快"。
- 与实时速度形成互补。

### 4. 新增独立 `TransferSpeedCalculator` / `TransferTask+Speed` 计算单元

**选择：** 将速度计算从 View 中抽离，放到一个独立可测试的结构中，供 `TransferTask` 或 `TransferStore` 使用。

**理由：**
- 便于 XCTest 覆盖正常/边界/错误路径。
- View 只负责格式化与展示，符合 MVVM。

### 5. 格式化与单位

**选择：** 速度单位自动切换：B/s、KB/s、MB/s、GB/s；使用 1024 进制，保留 1 位小数（小于 10 时）或整数（大于等于 10 时）。

**理由：**
- 与现有 `formatBytes` 函数的风格保持一致。

## Risks / Trade-offs

- **[Risk]** 轮询间隔不均匀导致实时速度抖动。
  - **Mitigation：** 滑动窗口本身具有平滑作用；若抖动明显，可延长窗口到 3 秒或做简单移动平均。
- **[Risk]** 任务刚开始时总速度可能显示为极大值或 0。
  - **Mitigation：** 已传字节为 0 时总速度显示为 0；时间差极小但字节数非零时按实际计算即可，通常只在首帧出现，可以接受。
- **[Risk]** 暂停/失败任务的速度未及时归零。
  - **Mitigation：** 当任务状态不是 `running` 时，不再加入新的进度点，实时速度使用窗口内最后有效数据计算，最终自然衰减到 0；UI 也可在状态为非运行态时直接显示 "0 B/s"。

## Migration Plan

无需迁移。本变更仅新增展示字段与 ViewModel 计算属性，不影响已有传输任务的数据结构持久化。
