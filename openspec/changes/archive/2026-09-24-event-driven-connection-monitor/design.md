## Context

见 proposal.md。现有遥测更新统一经过 `TelemetryRegistry`；生命周期日志只覆盖部分事件，不能作为页面状态源。`snapshot()` 还计算 250ms 窗口速率和五秒空闲判定，这两个时间派生状态不能在删除轮询后冻结。

## Goals / Non-Goals

目标是消除固定轮询延迟和空态闪动，保持当前快照字段、手动刷新、按需健康检查及稳定卡片身份。最新状态可以合并投递，不承诺每个中间态都绘制一帧，也不承诺零线程调度延迟。

## Decisions

1. 核心注册表用已有 tokio watch 通知遥测修改。订阅先注册观察者，再读取初始快照；等待期间的修改保留为待处理通知。订阅比较完整快照，只返回实际改变的值。状态修改锁内只发送内部唤醒，跨语言回调在锁外执行。相比复用可被 drain 的生命周期队列，此方案覆盖所有字段且多个窗口互不消费对方事件。
2. 核心订阅在状态变化或最近一次派生状态到期时醒来。稳定空闲后的首个 I/O 开启新速率窗口，不能把整个空闲期作为新一轮采样时长。速率窗口有未结算字节或非零速率时设置窗口到期；Active 状态设置最后活动后五秒的空闲到期。时间使用单调时钟；每次醒来重新计算下一期限。没有连接或所有派生状态已稳定时只等待事件，没有固定周期任务。
3. 同步 UniFFI 订阅入口返回可取消对象；全局 runtime 运行核心订阅并向回调发送既有 DTO。取消及对象释放中止任务，不创建 runtime；回调只入队，不访问 UI 或等待主线程。已有同步 list 接口保留。
4. Swift 用容量为一、保留最新快照的 AsyncStream 将回调转到 MainActor。页面 task 管理订阅和取消，旧订阅的迟到值不得应用。首次快照结束加载；自动快照不修改手动刷新标志。手动读取与订阅竞态时，不允许较早读取覆盖已收到的新状态。
5. 手动健康检查完成后也读取核心完整快照，不用探测返回值在 Swift 拼接状态，以免覆盖核心后续的连接故障。核心在读取状态的同一把锁内分配快照顺序号，手动读取与订阅共用顺序。Swift 拒绝较小顺序号，覆盖“旧手动读取晚到”和“旧推送晚到”两个方向的竞态；顺序号不是 UI 推导的业务状态。后者的 XCTest 在修复前实际失败，随后补齐顺序元数据。

## Risks / Trade-offs

- [高风险：FFI 与取消竞态] → Rust 测试取消/释放，Swift 测试取消后迟到回调、重新挂载及多个订阅；生成绑定并双端编译。
- [空闲/速率停留在旧值] → 可控时钟测试一次性期限，确认归零/空闲后无下次期限。
- [突发流量积压] → 两端合并未消费快照，内存有界；保留当前累计字节和最终状态，监控不承担逐事件审计。
- [共享状态被快照读取改变] → 所有订阅独立计算期限并比较最新值；读取不触发网络操作。

## 评审

用户已要求以底层事件更新 UI。方案在实现前按架构清单自审：规则仍归核心，FFI 只桥接与管理订阅生命周期，Swift 只呈现；无新增平台分支、生产依赖或网络动作。拒绝仅隐藏加载动画及仅空态停止轮询，两者都不能满足实时事件更新要求。工作树开始实施时无既有未提交改动。

## Migration Plan

先记录失败测试，再实现核心订阅、FFI 与 UI，最后运行相关测试、Rust 全量/覆盖率、Apple 绑定和双端构建。同步 specs 并归档提案；兼容同步查询，回退无需迁移数据。
