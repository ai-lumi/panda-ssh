## Context

见 proposal.md。`TerminalCoordinator` 当前将首次尺寸上报与 `TerminalViewDelegate.sizeChanged` 绑定；视图先于异步 SSH 建连完成布局时，连接为空，已缓存尺寸不会在连接到达后重发。

## Goals / Non-Goals

**Goals:**

- 在共享 SwiftUI 终端桥接层为每个新 shell 连接补发最新已知尺寸。
- 保留窗口连续变化的既有去抖语义，并避免连接前遗留的延迟任务造成重复上报。
- 用不依赖真实 SSH 服务器的 XCTest 覆盖该时序。

**Non-Goals:**

- 不从视图像素尺寸重新计算行列数，也不修改 SwiftTerm、SSH core 或 FFI。
- 不扩大为连接重试或通用状态机改造。

## Decisions

### 连接挂载时使用已缓存的终端尺寸

协调器在连接对象由空或旧对象切换为新对象后，取消待执行的去抖任务；若已有有效尺寸，立即发送该尺寸。

理由：尺寸回调是 SwiftTerm 对实际网格的唯一权威来源。重读视图尺寸会重复换算逻辑且可能在布局中途取得不稳定值。

备选方案是在终端视图挂载完成后强制触发一次布局。该方案依赖 SwiftUI/AppKit/UIKit 生命周期，不能保证发生在连接可用之后，且会引入额外 reflow，因此不采用。

### 连接同步视为新会话的初始上报

缓存尺寸代表当前视图状态，而非某一旧连接的发送记录。每个新的 `ShellConnection` 都需要得到一次当前尺寸，以支持重连及初次异步建连。

理由：PTY 尺寸属于远端 channel 的状态，不能由上一条连接继承。

## Risks / Trade-offs

- [连接刚建立时尺寸仍为默认网格] → 仅发送 SwiftTerm 已报告的有效尺寸；后续真实布局变化仍按既有首次/去抖路径发送。
- [连接前的延迟任务重复发送] → 在连接同步前取消并清空待执行任务。
- [同步调用失败被忽略] → 沿用现有不因 resize 失败中断 shell 的策略；日志仍记录上层已有的可观测信息。

## Migration Plan

无需数据迁移。发布后，新建与重连的终端都在 shell 可用时同步当前尺寸；回滚只需恢复协调器的连接挂载逻辑。
