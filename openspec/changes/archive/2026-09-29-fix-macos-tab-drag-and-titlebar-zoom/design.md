## Context

见 proposal.md - Why。当前 macOS 主窗口使用隐藏系统标题栏和全尺寸内容区；`mouseDownCanMoveWindow` 的原生视图仅能发起窗口拖动，不能自动恢复原生标题栏的双击缩放。页签排序同时存在全局显示顺序、未分组顺序和各分组 `tabIDs` 三个有序集合，当前拖放仅修改其中一项，且在 `dropEntered` 时提前提交。

## Goals / Non-Goals

**Goals:**

- 将 macOS 窗口手势桥接限制在空白命中区，并明确双击仅对该区域有效。
- 将一次页签拖放建模为“开始快照 → 临时预览 → 成功提交或取消恢复”的事务。
- 由拖放源与目标所在的实际渲染容器决定更新哪个有序集合，避免显示顺序与数据不一致。

**Non-Goals:**

- 不用 `DragGesture` 替换既有跨平台拖放 API，不新增 AppKit 工具栏或恢复旧 UI 路径。
- 不让 macOS 专属窗口事件影响 iPadOS 的页签业务规则。

## Decisions

### 1. 空白区使用专用 AppKit 视图处理窗口事件

保留顶部 chrome 的显式空白区，并令其原生视图同时支持 `mouseDownCanMoveWindow` 与双击次数识别；双击时调用窗口标准缩放动作。页签和按钮不铺设该视图，也不通过透明拦截层“排除”窗口拖动。

理由：AppKit 在命中视图确定后决定窗口拖动；按区域提供唯一事件所有者比依赖 SwiftUI 背景层的命中顺序更可验证。标准缩放动作保留系统对当前缩放/还原状态的处理。

替代方案：将整个顶部 chrome 交由一个手势识别器，并在坐标上排除页签。否决：会重新引入命中竞争，且坐标随侧栏和溢出控件变化而脆弱。

### 2. 拖放只在 performDrop 时提交

开始拖放时保存受影响容器的原始顺序；`dropEntered` 仅更新局部临时预览，`performDrop` 才提交。取消、退出或来源失效时恢复快照并无条件清除拖拽状态。

理由：`dropEntered` 不是用户完成操作的证据；以提交点区分预览和状态变更可满足取消原子性。

替代方案：每次进入目标立即写入，并在取消时尝试反向移动。否决：目标多次进出、页签关闭及分组变化会使逆操作不可靠。

### 3. 依据渲染容器更新顺序

未分组拖放更新未分组有序集合；同组拖放更新该组的有序集合。跨组移动不在本变更范围内，遇到跨组目标不提交排序。完成后从同一规范化顺序派生显示和键盘导航。

理由：当前分组渲染直接读取组内集合，修改独立全局映射无法改变界面。限制跨组语义避免在修复中暗自新增“移动到分组”的产品规则。

替代方案：仅保留全局 `displayOrder` 并每次渲染重新投影到分组。否决：需定义分组间相对顺序和重复/缺失 ID 的冲突规则，复杂度不符合本次范围。

## Risks / Trade-offs

- [Risk] 自绘 chrome 的空白区在窗口尺寸变化后为零宽或被控件占满 → 仅为实测非零空白矩形安装原生事件视图，并在窗口尺寸/侧栏状态测试中覆盖。
- [Risk] 原生双击与连续拖动的时序不同 → 以 AppKit 事件单元测试验证单击拖窗、双击缩放和控件区不缩放三条路径。
- [Risk] 拖放期间页签同步关闭 → 在提交前重新验证来源与目标，失效时恢复可用快照并清理状态。

## Migration Plan

1. 先加入失败测试，锁定命中区、双击缩放和拖放事务语义。
2. 实现原生空白区桥接与排序事务，保持 Rust/FFI 不变。
3. 运行 macOS XCTest、iPadOS 相关 XCTest、Rust 测试和覆盖率门禁；再进行受控人工验收。
4. 回滚时可撤销此提案的 Swift 改动；不涉及数据迁移或持久化状态。
