## Context

当前工作区内部状态只保存页签 ID、主机、类型和连接状态；列表读取时才根据当前数组顺序生成标题。这使标题成为易变的展示派生值，而不是页签的生命周期属性。详见 proposal.md 与 workspace 规格增量。

## Goals / Non-Goals

**Goals:**

- 在 Rust 工作区状态中保存创建时分配的页签标题。
- 为同一主机的新页签分配不与当前打开页签冲突的最小可用序号。
- 保持 FFI 和 Swift UI 仅消费 Rust 所返回的稳定标题。

**Non-Goals:**

- 不改变主机名称更新后的现有标题行为以外的主机编辑工作流。
- 不保存跨进程页签或引入永久序号计数器。

## Decisions

### 将完整标题保存到工作区内存状态

`InternalTab` 保存创建时确定的完整标题，列表读取直接返回它。这样关闭、排序、分组和同步都不会重新解释页签身份。

替代方案是在 Swift 层缓存标题。该方案会将平台无关业务规则复制到 UI，并会在未来 Linux 客户端或任何非 Swift FFI 消费者上失效，故不采用。

### 新建时复用当前未占用的最小序号

为某主机创建页签时，先收集其当前打开页签的标题，分配基础标题或最小未占用的正整数后缀。关闭页签后，该页签的序号可以被下一次新建复用；已打开页签不改名。

替代方案是维护单调递增计数器。它避免序号复用，但需维护额外状态，并会在短生命周期工作区中产生不必要的大编号，超出本变更需求。

### 纯函数负责标题分配并以单元测试锁定契约

将标题分配保留为 `panda-core` 的平台无关纯函数，FFI 状态只在创建时调用。测试覆盖正常创建、关闭后稳定、序号复用和多主机隔离。

## Risks / Trade-offs

- [主机名称在页签打开后被编辑] → 既有页签保留创建时标题，以满足稳定性；新页签使用新名称。这是可预期的会话快照语义。
- [同名主机标题含类似 "(2)" 的文字] → 分配依据当前已保存的完整标题比较，不解析用户输入名称的文字结构，避免误判。

## Migration Plan

这是仅内存态的行为修复，无持久化数据迁移。回滚到旧版本只会恢复动态重编号，不影响主机配置、会话数据或凭据。
