## Context

动机与行为契约见 [proposal.md](proposal.md) 及 `config-export-import` delta。现有导入在完成 manifest 和必需文件检查后，逐条将归档名称与配置根目录拼接，并在同一循环中备份、创建父目录和写入；因此不可信名称会参与文件系统操作。FFI 导出保持同步，Swift 的 macOS/iPadOS 共享调用路径只接收导入结果或错误。

## Goals / Non-Goals

**Goals:**

- 在任何可变文件系统操作前，以确定性规则验证整个归档的条目集合。
- 将有效归档的恢复、备份、统计和非 ASCII snippet 文件名行为保持兼容。
- 让 core 产生可测试的安全错误，FFI 继续通过既有错误映射传递给两端 UI。

**Non-Goals:**

- 不限制压缩后/解压后大小、压缩率、条目数量或导入内容的 TOML 语义；这些需要独立的资源限制和配置校验设计。
- 不支持任意目录树或未来未知文件的前向兼容导入；新增可导入文件类型时必须先修改规格和白名单。
- 不处理本地攻击者预先将私有配置目录替换为符号链接或与导入进程竞争文件系统的场景；该模型已超出 ZIP 条目控制的威胁边界。

## Decisions

### 1. 采用显式白名单，而非仅做路径净化

预检将允许的归档逻辑路径限定为根目录固定文件和 `snippets/<filename>`。`snippets` 文件名必须为单一、非空的文件名；任何目录条目、额外 `/` 层级、`.`、`..`、平台歧义的分隔符或不在集合内的根目录文件都拒绝。每个被接受条目生成唯一的规范化相对目标名，并用集合检测重复目标；`manifest.json` 也必须唯一。

替代方案是使用 ZIP 库的安全路径辅助函数，或在拼接后检查最终路径前缀。前者若静默净化名称会使不同恶意名称别名化为同一文件，后者仍允许本产品从未承诺支持的文件进入配置目录。白名单同时表达归档格式契约并消除歧义，复杂度最低。

### 2. 校验与提取分两阶段进行

第一阶段读取 manifest、ZIP 元数据及每个允许条目的完整内容，以在变更本地配置前触发解压和 CRC 错误；检查全部条目、重复项、必需文件和版本。任何归档输入失败立即返回安全或格式错误，且不得调用创建目录、重命名、备份或写入 API。第二阶段仅使用预检得到的允许相对路径和已校验内容进行现有备份和写入流程。

替代方案是在现有提取循环中逐项校验。它会让归档中排在后面的恶意条目发生错误前，已修改先前配置文件，违反损坏归档不修改本地配置的契约。

### 3. 安全错误保持在 core，FFI 契约不扩张

`panda-core` 为不安全归档条目提供专门的导入错误变体；错误对 UI 是可区分的，但不必回显攻击者控制的完整条目名。`panda-ffi` 继续将 core 错误转换为既有 `PandaError::Core`，不新增异步运行时、平台类型或 Swift 业务分支。

替代方案是在 Swift 文件选择后预筛归档。该方案无法保护其它 FFI 调用者，也会使 macOS/iPadOS 行为分叉，因此不采用。

## Risks / Trade-offs

- 合法但未列入白名单的历史或手工归档将被拒绝 → 当前导出只产生允许集合；如确有兼容需求，先以样本和规格变更扩展白名单。
- ZIP 条目路径命名在不同平台有差异 → 以 ZIP 逻辑路径的严格格式验证，拒绝有歧义的分隔符和层级，不依赖宿主平台的路径归一化。
- 预检需要完整读取所有条目并暂存内容 → 配置归档规模很小，额外 I/O 与内存换取无部分导入的安全性；不以此提案处理大归档资源耗尽。
- 现有备份命名可能与主规格文字不同 → 本变更仅确保预检发生在备份之前，不借机改变备份格式，避免扩大安全修复范围。

## Migration Plan

1. 先为合法、路径逃逸、绝对路径、非允许层级、重复目标和外部既有文件编写失败测试，记录 red 结果。
2. 实现纯条目验证与全量预检，再让提取阶段只消费已验证的目标；使测试转绿并做最小重构。
3. 运行 Rust 测试及覆盖率门禁；FFI 签名不变时不需要生成新的接口，但仍按项目构建门禁验证受影响平台。
4. 回滚仅撤销本变更；它不迁移用户数据，也不改变有效归档格式。已被拒绝的非白名单归档必须在评审后才考虑兼容方案。
