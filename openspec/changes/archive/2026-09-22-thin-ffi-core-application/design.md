# 设计：可独立调用的核心应用服务与薄 FFI

## Context

动机与范围见 [proposal.md](proposal.md)。本次以当前源码和 `openspec/specs` 为证据，旧提案的已勾选任务不等价于当前验证结果。此次仅编写文档，未运行 Rust/Swift 测试，不能宣称基线全绿。

关键现状：

- `ffi_transfers.rs` 持有 `TransferTask`、并发信号量、状态转移与组聚合；`batch_transfer.rs` 持有独立注册表、冲突通道及 300 秒超时后跳过策略。核心已有传输、批量扫描/执行和速度算法，但没有对应的完整任务服务。
- `ffi_store.rs` 持有 `Stores`，执行路径装配、权限策略、凭据构造和删除主机的补偿；`PandaCoreBackend.saveHost` 仍编排凭据写入、主机保存及旧引用清理，`CredentialResolver` 仍决定手动输入优先级。
- `ffi_workspace.rs` 持有标签、关闭确认、终端状态及 TOFU 容器；`WorkspaceStore` 同时维护显示顺序、分组和确认判断，并在关闭前写入 inactive 绕过 FFI 确认。`TerminalSessionStore` 仍维护实际连接代次；`AppModel.pendingTofu` 是 Swift 生产路径的确认等待队列。
- `SftpSessionStore.upload/download` 虽调用核心扫描和聚合，却仍决定文件/目录走哪类任务、逐项入队和冲突后动作；本地/远端删除循环也留在 Swift。
- 核心已有 `delete_tasks.rs`、`task_summary.rs`；存在这些类型不代表生产路径已接通。实施需追踪真实装配，保留已有退出交互，仅将其业务停机动作接入核心。
- 覆盖率脚本和契约矩阵硬编码 FFI 文件名及测试名，模块边界脚本要求批量任务属于 FFI 模块树。迁移必须同步更新这些验证依赖。

### 已发现的约束差异

| 差异 | 本提案处理 |
| --- | --- |
| `ffi-bridge` Purpose 说薄桥，但 Requirement 把“业务 FFI”视为固定归属 | 用本次 delta 明确目标边界，并让覆盖责任随代码迁移 |
| `workspace` 的“标签页会话关联”仍描述共享连接/延迟断开，与 `connection-pool`、`transfers` 和同文件后续“精确关闭”条目冲突 | 本次修改该条目，统一为现有独立所有者模型，不能恢复连接池 |
| `tab-groups` 写“不持久化到 Rust 侧或磁盘” | 明确核心内存所有权与磁盘持久化不同；继续不落盘 |
| `AGENTS.md` 部分旧段仍提钥匙串、初始化 no-op 和 AppModel TOFU 所有权 | 按当前凭据/FFI specs 保留文件凭据及可重新初始化契约；实施收尾同步更新架构说明 |
| `AGENTS.md`/config 的通用 95% lines/regions 与当前 FFI 专用 raw regions 诊断规则不完全一致 | 不降低任一门禁。实施同时运行现有分层脚本及仓库要求的 workspace 聚合阈值；FFI 不新增逐文件 raw regions 阈值。不能以本次薄桥迁移暗中扩大排除范围 |
| `AGENTS.md` 写 `## Requirement`，CLI 实测只解析 `### Requirement` | 文档使用与当前 specs 一致的三级 Requirement、四级 Scenario；保留严格校验能力，不改工具或绕过校验 |

## Goals / Non-Goals

目标：从任一平台适配器移除 UI/FFI 后，仍可通过核心公共入口执行同一业务操作；业务状态、决策与测试有唯一明确归属。最小架构仍是现有两个 Rust crate，按领域模块逐步迁移。

设计边界：不为每个类型增加 trait，不将所有方法塞进巨型门面，不机械要求每个 FFI 函数一行；不迁移 UI 几何、焦点、文本编辑草稿或原生授权 API。进程级日志/遥测可在核心保持已有机制，必须标注作用域，不能用“核心可构造”宣称所有现有全局观测数据天然隔离。

## Decisions

### 1. 以业务可独立复用为归属判据

移除 UniFFI 和 Swift 后仍然必须成立的校验、业务身份、状态转移、调度、故障处理、安全策略及持久化流程，放入 `panda-core`。UI 手势产生操作意图，核心执行规则，UI 呈现结果。例如标签拖动坐标属于 UI，标签移动后的逻辑顺序及关闭相邻选择属于核心；选择哪些文件属于 UI，选择结果如何扫描、组任务、处理冲突属于核心。

仅将纯算法移入核心不够：如果新前端需要复制 `run_transfer_task`、主机凭据写入顺序或 TOFU 等待队列，仍判定该用例未下沉。仅重命名 `panda-ffi` 或新增另一个业务 crate 也不满足用户指定的归属。

### 2. 核心应用入口负责装配，领域服务负责状态

在 `panda-core` 增加应用服务模块（建议 `application`），提供可构造的 `PandaCore` 上下文，按需求组合配置/凭据、连接、传输/删除、工作区服务。名称可在实现中调整，验收约束的是能力和依赖方向。

依赖方向：Swift/UI → FFI → 核心应用服务 → 核心领域与 I/O；Rust 原生宿主直接从核心应用服务进入。核心类型不使用 UniFFI derive 或 `PandaError`，领域服务不调用 FFI helper。

`PandaCore` 接收配置根、存储位置类别、所需外部依赖与执行器句柄；FFI 延续单个懒初始化 Tokio runtime，核心不自行创建第二个 runtime。Rust 宿主可提供自己的 runtime。仅在需要 fake I/O、可控时钟或资源提供者时引入窄 trait，复用既有 `ConfigStore`、`GroupStore` 等边界。

核心上下文区分：进程观测服务、应用存储、工作区状态、单会话与单任务资源。两个测试上下文的业务数据和任务隔离；不要求本次实现多窗口产品能力。兼容 `init_store` 可替换 FFI 默认上下文引用，存活操作必须持有原上下文，不能在工作过程中重新查询全局 store。旧任务结束后释放原上下文，不能因切换目录取消其他所有者。

### 3. 配置操作表达意图，写入规则集中

核心提供保存主机及凭据、删除主机、复制主机、组移动等已存在的完整用例。新增输入区分“保留、设置、移除凭据”，避免把未编辑的空表单误认为清空操作；具体空值语义对照当前 `auth`、`credential-protection` 和配置规格，先写特征测试。

核心统一决定引用命名、认证方式切换、写入顺序和补偿。错误保留阶段与类别；补偿失败不能覆盖原始失败事实或报告成功。迁移不宣称跨多个 TOML 文件具备崩溃原子性，也不引入数据库或事务日志。

目录位置由平台提供。通用的常规文件/符号链接校验、凭据 `0600`、专属配置目录 `0700` 等保护由核心执行；App Group 容器不能 chmod 的差异使用明确的存储位置类别或窄平台适配表示，不将 `cfg!(target_os = "ios")` 业务策略原样搬入核心。已存在的保护机制和文件格式保持。

### 4. 连接与交互请求由核心拥有

核心连接服务接管凭据解析、未知密钥处理、TOFU 等待者、连接代次、取消/重试及精确资源释放；会话资源本身继续复用已有 `SshSession`、`ShellSession` 和 `SftpClient`。

交互输出采用简单值表示：请求 id、所属业务对象/代次、待确认或待输入种类及必要公开字段。UI 响应携带请求 id 和用户选择。核心验证有效性并推进状态，迟到回应不影响新的操作。绑定可通过快照/轮询或已有异步包装递送这些请求，不要求引入通用事件总线或强制推送。

TOFU 共享确认绑定到地址、端口、呈现密钥和有效请求。持久化成功后才广播成功；呈现者消失不能使等待者悬挂。暂存秘密不出现在快照、日志、错误或例外清单；每个会话独立使用手动输入，传输只持有其显式授权所需输入。需支持失败重试的任务，其秘密保留策略需由核心明确管理，任务清理后不能靠 FFI 注册表残留续存。

当前传输和扫描代码硬编码 `AcceptAndStore`，普通连接则接受显式策略参数。这是已观察到的入口差异，不能断言用户路径已经安全。实施先验证 UI 前置确认及 known_hosts 变化竞态；以当前 `host-keys` 的未确认不认证约束统一核心路径。显式 `trust_on_first_use=true` 保留其公开参数语义，无该授权的入口不能自行选自动信任。修正偏差需记录为安全规格对齐及针对性 red-green 测试，不把现状无条件作为兼容依据。

### 5. 迁移完整任务服务，保留领域差异

先迁入单文件任务注册、调度、合法控制操作、进度版本和速度；再迁入批量注册、冲突等待/超时/取消与收尾，最后接入 Swift 中的扫描→聚合→入队及删除流程。先复用现有核心执行算法，避免同时改写协议层。

单文件与批量任务可有不同内部执行器，业务归属同一核心领域不等于强制合并所有类型或并发预算。现有单文件并发上限 3、运行暂停占槽、排队暂停不占槽、重试复用 id 等需逐项验证。批量 300 秒冲突超时和既有字符串错误属于待核对的实现行为；若当前规格未定义，先记录特征，不借迁移擅自改变其外部结果，策略归属迁入核心。

工作流保持 scan/transfer/delete 的取消作用域，源 SFTP 标签关闭不影响任务。复用已有删除与工作摘要代码，但必须验证生产调用已接入；不因存在未接通的模块就把其他未评审提案中的新 UI 或远端执行功能纳入本次。应用退出的手势、提示和系统退出调用留在平台，接纳新任务/取消/释放等业务停机由核心执行。

状态修改与快照需避免多个锁之间读出互相矛盾的状态。核心不持有全局业务锁跨网络 await、用户等待或回调；UI 不在主线程执行阻塞 FFI，异步结果回主线程只做呈现。先以可控 fake/时钟验证竞态，再保留 fake-server 集成用例。

### 6. 工作区与会话有一致身份，UI 保留原生状态

将 `WorkspaceState` 迁入核心，并吸收 Swift 中影响业务的逻辑顺序、分组关系、确认请求、连接状态与重试代次。核心返回打开/关闭/待确认等结果，负责协调相应资源服务；调用方不能先伪造 inactive 再关闭。

关闭请求记录目标集合及会话代次，避免确认期间新标签或重连被旧授权关闭。核心拥有逻辑活动标签及共享顺序，Swift 的 `tabs`、`activeTabID` 等仅为快照；拖拽中的预览位置、滚动可视区、终端焦点、页内选择和窗口导航由 UI 持有。

分组进入核心内存不会增加持久化需求。现有 Swift `ObservableObject` 可继续存在，但只能转发命令、订阅/刷新、转换显示数据和管理纯 UI 状态。测试替身可模拟结果，不要求 Preview 启动网络；不得用只验证 mock 状态机的测试替代真实核心和桥接契约验证。

### 7. FFI 保留范围是小型白名单

| 允许职责 | 必要原因 | 允许持有的状态 | 核心必须负责的部分 |
| --- | --- | --- | --- |
| DTO/错误/路径表示转换 | 跨语言类型限制 | 无业务状态 | 输入业务校验、错误分类、路径语义 |
| 同步/异步适配 | 当前同步 UniFFI 契约 | 单个 runtime 及调用等待对象 | 调度、业务超时、重试和取消语义 |
| 默认核心实例装配 | 兼容全局导出 | 核心引用及初始化同步 | 存储构造、权限、上下文隔离 |
| 不透明资源句柄 | 兼容整数 handle API | handle → 核心资源引用 | 状态机、所有者、精确关闭和释放 |
| 请求/快照投递 | 跨语言线程和回调约束 | 最小投递关联与包装生命周期 | 待确认业务状态、响应有效性与超时结果 |

原生文件选择器、security-scoped URL、剪贴板、键盘和窗口 API 属于 Swift 平台适配，不是 FFI 可扩张业务的理由。已批准的平台访问范围通过窄接口或资源引用提供给核心；适配器可执行“读这个目录/删这个文件”的 I/O，不执行“递归删哪些项目/遇错是否继续”的规则。

实施须建立例外登记表，逐项填写路径/符号、技术限制、最小状态与作用域、释放方式、替代方案、正常/失败/边界测试、复审触发条件。上表是允许的职责类别，不等价于预先批准任何现有大模块。不得以测试注入、方便访问 store 或尚无核心 API 为例外。

## Risks / Trade-offs

- [高风险：认证与持久化] 状态迁移可能改变凭据优先级、信任策略、回滚或文件权限 → 逐入口对照当前规格并用失败注入验证；不用真实用户凭据作测试。
- [高风险：并发与所有权] 取消/重试/回调和初始化切换可能串用资源 → 核心实例引用固定、请求代次明确、独立所有者、锁外等待和迟到清理测试。
- [风险：兼容接口继续被组合使用] 核心完整用例已存在但 Swift 仍走旧编排 → 验收检查生产调用链，保留旧 API 不等于保留旧业务所有权。
- [风险：过度集中] 巨型核心上下文难测试、全部交互串行化 → 门面只装配，领域对象分责，业务接口按用户操作粒度设计。
- [风险：行为偏差夹带修改] 历史 specs 与代码冲突 → 在切片任务中登记现状、权威条目和目标，未解决不宣称行为等价；新增产品行为另走提案。
- [成本：跨端验证] Rust 测试通过不能证明 Swift 调用正确 → 保留契约测试和双端构建/XCTest，不将 Linux 编译成功表述为 Linux UI 已验证。

## Migration Plan

按 tasks 顺序做可验证切片：先建立核心上下文与边界测试，再迁配置/凭据、连接/确认、单文件任务、批量任务、文件操作、工作区和停机，最后完成契约/覆盖率与双端验收。每个切片均先 red，再最小实现 green，再移除真实调用方中的重复规则；不机械重跑所有构建来发现依赖。

旧公开 FFI 在迁移中转发到新核心，新增完整用例入口为 UI 提供收敛点。每个业务对象在任一时刻仅一个权威管理器，禁止旧/新状态机双写。迁移期间维护旧符号→核心入口→适配器→测试清单。

回退粒度为完整切片（核心、桥、调用方、测试及规格），保留版本控制可追踪变更，不依靠破坏性恢复命令。无持久化格式迁移，因此无额外数据降级步骤；回退不能恢复已修正的不安全信任路径或失效权限策略。

## Verification 与 Validation

| 检查 | 验证的问题 | 通过标准 |
| --- | --- | --- |
| OpenSpec 严格校验与需求/任务核对 | 此次文档能否被解析且覆盖六项能力 | 所有 delta 可解析、所有修改条目存在、每个需求有场景及实施任务 |
| 核心单元及 fake 流程测试 | 规则是否已独立于绑定 | 每个切片正常/意外/边界通过，测试直接调用生产核心入口 |
| 无 UI 宿主 + FFI 对照 | 新前端是否能复用完整用例 | 同序列状态、错误、确认和资源结果一致；核心宿主无 FFI 依赖 |
| 静态边界检查 + 人工调用链审查 | 是否残留业务外泄 | 生产领域清单闭合，例外逐项可解释；正则扫描仅作辅助而非证明 |
| `cargo test --workspace` 与覆盖率门禁 | 回归和覆盖归属是否正确 | 全绿；核心 lines/regions ≥ 95%，FFI 包级/保留适配文件 lines ≥ 95%，契约矩阵齐全 |
| 仓库通用聚合覆盖率命令 | 是否满足 AGENTS/config 更严格的聚合要求 | `cargo llvm-cov --workspace --tests --fail-under-lines 95 --fail-under-regions 95` 通过；不以架构变更降低阈值 |
| `cargo check -p panda-core --target x86_64-unknown-linux-gnu` | 非 Apple 核心是否可编译 | 无平台专属依赖；若本机缺工具链，在支持环境运行后才标记通过 |
| build-rust.sh → xcodegen → 双端构建及相关 XCTest | 绑定、线程与平台接入是否闭合 | macOS/iPadOS 构建通过，改动逻辑的 XCTest 通过 |
| 双端用户场景验证 | 是否仍支持实际操作目标 | 首次信任只确认一次、拖拽后关闭目标正确、标签关闭后传输继续、冲突/失败可处理 |

此次文档的 Verification 不等于实现已通过上述门禁。最终 Validation 是另一前端能够直接使用核心获得同样业务行为，原生 UI 的交互与呈现仍符合平台需求。
