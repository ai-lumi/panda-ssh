## Context

见 proposal.md - Why。当前 `ConnectionMonitorStore.refresh()` 每秒从同步 FFI 读取完整快照，并在主线程无条件替换 `records`。`ForEach` 已使用稳定连接 ID，但整表发布及 `ViewThatFits` 的自适应状态徽章仍会造成不必要的布局计算与卡片高度变化。

## Goals / Non-Goals

**Goals:**
- 在不改变 Rust 遥测与 FFI 契约的前提下，只向 SwiftUI 发布实质变化。
- 保持连接及通道的稳定排序和卡片结构，减少刷新期间的视觉跳动。
- 用 XCTest 验证空快照、无变化、单项更新与增加/移除连接的边界。

**Non-Goals:**
- 不实现跨 FFI 的推送订阅或修改连接遥测采集方式。
- 不将监控刷新转换为网络健康探测。

## Decisions

### 决策 1：在 Swift Store 进行可展示快照的相等性判定

将 FFI 返回的记录与当前记录作 `Equatable` 比较；完全相等时不写入 `@Published records`。这直接修复无变化也触发渲染的问题，且无 Rust/Uniffi API 变更。

替代方案：在 Rust 维护全局版本号并导出增量接口。它可进一步降低跨 FFI 数据复制，但需要跨层协议与生命周期语义，当前连接数很小，复杂度超过收益。

### 决策 2：以稳定 ID 合并有变化的快照

新快照按 Rust 已保证的连接 ID 排序；Store 按 ID 保留没有变化的现有值，只替换变化/新增记录并删除消失记录。`ForEach` 的 ID 与此一致，使 SwiftUI 可以保留未变卡片的身份。

替代方案：继续整体赋值并依赖 SwiftUI 自动 diff。其无法抑制相等快照发布，也不表达“未变项必须保留”的意图。

### 决策 3：状态徽章固定为单一纵向排列，动态数值使用等宽字形

移除会按可用宽度切换 HStack/VStack 的 `ViewThatFits`，统一使用纵向徽章排列；流量已使用 `monospacedDigit`，补齐动态时间/状态区域的稳定约束。牺牲少量横向紧凑性，换取在窄窗和文本变化时可预测的卡片高度。

替代方案：固定三枚徽章横排。窄窗口与本地化文本会截断或迫使意外换行，仍存在高度跳动。

## Risks / Trade-offs

- [FFI 记录类型不声明 `Equatable`] → 在 Swift 定义仅用于展示比较的显式相等函数，逐字段覆盖所有页面字段；测试在字段变化时断言会发布。
- [时间戳与速率本身可能每秒变化] → 有真实字段变化时允许更新卡片；固定结构避免其变成整页跳动。
- [合并代码遗漏新增或释放的连接] → 为新增、删除、排序和重复刷新覆盖测试。

## Migration Plan

1. 先新增失败的 Store 测试，证明相同快照不会改变已发布集合，且单项变更保留其他记录。
2. 实现相等判定与稳定合并，移除动态横/竖徽章切换。
3. 运行相关 XCTest 与 macOS 构建；失败时可回退至现有整表快照赋值，不影响连接或遥测数据。
