## Goals / Non-Goals

**目标**：用一份 core 诊断贯穿 Transport、Shell、FFI 和日志；把非致命输入拒绝与会话终止分开；支持可控故障注入，验证根因不会在清理中丢失。

**设计边界**：不根据命令文本推断退出，不新建运行时，不在 Swift 重复实现队列或故障分类，不引入远端探测、自动重试发送或全局 panic hook。后台任务监督只覆盖可捕获的任务退出，进程 abort 与强制杀进程不在保证内。

## Decisions

### 1. 结构化原因由 core 生成

在 core 定义共享的会话诊断值，供 Shell 终态、遥测和日志引用；FFI 只映射简单值类型。建议字段为：事件标识与发生时间、连接标识、所有者关联、操作阶段、原因类别，以及可选的 `io_kind`、`os_code`、`disconnect_code`、`exit_status`、标准信号类别。仅真实关联存在时填写 channel 与建连代次，不伪造未知字段。

阶段至少覆盖连接、认证、输入接纳、通道发送、Socket 读写、远端退出、窗口调整、后台任务和清理。原因至少区分正常退出、未知远端关闭、非零退出、信号退出、输入背压、输入过大、EOF、I/O 故障、keepalive 超时、协议错误、本地关闭和内部任务错误。固定中文消息由这些字段生成；未知库错误以安全未知类别表示，不格式化原始载荷。

原始远端描述、任意信号名称、错误字符串和 panic payload 不进入诊断。系统 I/O 类别与数值码可以保留；标准信号使用白名单枚举，未知信号映射为未知。日志中的错误描述是可解释的类别与安全字段，并非全部删除原因，也不依赖对任意文本进行正则脱敏。

替代方案：直接打印 `Debug` / `localizedDescription` 最省代码，但可能泄漏数据；继续固定通用文本不能定位原因。选择类型投影，新增依赖库错误时只扩展映射与用例。

### 2. 终态收敛与任务监督

Transport 和 Shell 共用每个会话的故障上下文。Socket 读写或 keepalive 先写入具体故障，再传播错误；上层收到通用通道错误时复用该原因。保留首个具体故障；缺少原因的占位可以由稍后到达的具体证据补充，但不能反向覆盖。每条失败事实与清理事实分别有事件标识，主因固定，清理事件附关联而非冒充用户操作。

Shell 收集 ExitStatus、ExitSignal、EOF 和 Close，关闭时结合已有 Transport 故障做终态判定：

| 证据 | 最终展示 | 日志 |
| --- | --- | --- |
| 零退出码 + Close，之前无故障 | 正常结束 | info |
| 非零退出码或标准退出信号 + Close | 远端异常结束，附码或信号 | error |
| 只有 Close | 远端已关闭，原因未知 | warning |
| I/O / keepalive / 协议故障 | 对应具体失败 | error |
| 健康会话被用户关闭 | 本地关闭 | info |

单独 EOF 不代表完整会话结束；读接口先排空已有输出，下一次无输出读取返回已存终态，写接口在终态立即拒绝。UI 保留既有关闭/失败面板与手动重试，仅细化原因；旧代次回调继续受 generation 与句柄校验约束。

后台工作任务返回明确结束结果，由独立监督路径观察任务完成及 JoinError，在既有 tokio runtime 执行。任务 panic 或非预期取消走同一故障发布与资源回收路径；本地 close 先设置关闭意图，再取消任务。不得仅在用户下次 write 或显式 close 时才发现任务已经退出。关闭持续保持有界，不依赖输入队列空位。

关闭意图与“一次有效 Transport 关闭”使用同一个原子终态门控。任意入口先执行 compare-and-set：第一个成功者记录意图/终态并拥有关闭动作；后续入口只读取既存终态并完成自身清理。这样不依赖 `is_closed()` 作为并发排他手段。只有已有本地关闭意图时，EOF、取消和断开回调才能标记为清理；若 Closed 先发生但没有本地关闭意图，后来的具体 I/O 或 keepalive 证据仍可补全原因。

Swift 状态拆分为“连接失败”和“会话已结束”，或在既有状态上携带明确终态枚举；正常退出的标题、图标和工作区连接状态不得复用失败语义。两者都不再允许输入，也都释放句柄；工作区关闭确认仅将活跃 shell 视为连接中。

### 2.1 锁中毒与跨会话隔离

输出缓冲锁及 FFI 会话表锁不得使用无条件 `unwrap()`。锁中毒需要被转换为所属会话的内部错误，并恢复或移除受损会话；会话表读取时不得在持有全局锁的同时调用可能取得会话内部锁、等待网络或触发回调的操作。先复制必要的会话引用或借助细粒度同步，再在表锁外执行读、写和关闭，避免一个中毒缓冲区把全局表锁一并毒化。

替代方案是吞掉中毒并继续读取缓冲区。它会让已经未知一致性的输出被当作可靠内容，且隐藏 bug；选择将受损会话转为内部故障、其他会话继续可用。正常 Mutex 竞争仍是短暂同步，不应被误报为失败。

### 3. 输入队列采用非阻塞的整块拒绝

保留有界队列，建议初始限制为 64 个待发送块、每会话 1 MiB 待发送字节、单次写入不超过 1 MiB；这是本地内存预算，不是网络性能指标，可通过集中常量与测试注入调整。字节预算包含发送中的未完成块，入队前原子检查并预留；发送完成、拒绝、失败和取消时释放，不允许多调用者穿透上限。

`write` 成功表示整块被接纳。Full 返回独立 `InputBackpressure`；超过单次上限返回 `InputTooLarge`；Closed 返回已存终态。输入拒绝不修改连接健康状态。Swift 显示“输入缓冲区已满，本次输入未发送”或“输入过大，本次输入未发送”，不调用会话关闭入口；同一连续拒绝时段合并提示与 warning 日志，计数允许记录，字节内容不记录。再次成功接纳后重置提示抑制状态。

不在 Swift 保留第二份待发队列，不自动重放拒绝或发送结果未知的输入；一次粘贴被拆为多次调用时，已接纳的早期块可能已到远端，拒绝提示仅承诺本次调用未发送，不能声称整次粘贴被回滚。

替代方案：无界队列会把慢连接变成内存增长；等待队列容量会阻塞同步 UI 输入；单纯增大 64 只能推迟问题。选择明确拒绝与保活，接受极端输入时用户需要根据提示自行处理的成本。

### 4. 生命周期直接进入同一个日志服务

将统一日志实例归属 core，由 `init_store` 配置持久化目录；FFI `log_write`、日志查询和 SSH 事件使用同一实例。事件产生时分配稳定标识与发生时间，将安全投影写入日志，并按现有上限保留生命周期查询队列；移除 Swift 将已记录事件再次 `logWrite` 的路径。

生成事件快照后释放连接注册表锁，再提交日志；日志服务不反查遥测，避免锁循环。输入调用只完成短时内存操作；文件操作在串行后台执行上下文处理，复用既有运行时调度，不另建 tokio runtime。文件待写队列设明确上限，超限与 I/O 失败同样进入可观测的持久化降级路径，不无限累积，不阻塞 UI 等待磁盘。

日志记录增加 core 分配的单调标识；FFI 保留最新在前的查询契约。Swift 按标识适配为旧到新，复用标识，不再每次生成 UUID；仅集合或字段改变时发布 UI 状态。`LogView` 使用换行文本展示完整消息，滚动目标为实际新增的末条。

替代方案：仅在 Swift catch 中补日志仍会漏后台事件；继续把事件持久化交给 Swift 轮询仍有消费时序问题。直接写统一日志可减少桥接环节，不增加第二套文件日志。

### 5. 文件日志故障与路径兼容

规范路径统一为配置根下 `logs/panda-ssh.log`，轮转保留 `.log.1`；不迁移或清空旧根目录日志。日志先于 store 初始化时先存内存，目录配置成功后按标识补写仍保留的未持久化条目，再接续新事件。不得因 `OnceLock` 首次取到空路径而永久禁用持久化。

文件创建、追加、轮转经可注入存储边界串行执行。只有写入成功才推进持久化游标与文件大小；失败不删除原文件，不递归将故障写入同一失败文件。内存中维护一次连续故障的状态和计数；相同故障合并，恢复时记录恢复及可能缺口。普通磁盘失败不自动重放可能部分写入的历史记录，仅继续新记录，避免重复与无依据的完整性承诺。初始化前的未写入记录与写到一半失败的记录应明确区分。

## Risks / Trade-offs

- 输入暂满是否为现场根因仍未知 → 先用可控队列确定性验证误关路径，实际故障通过新诊断验证，不以“没有再遇到”充当根因证明。
- 同时出现多个结束信号存在竞态 → fake 明确控制事件顺序，覆盖具体故障与 Close 的两种顺序、显式关闭后的取消、旧代次回调。
- 关闭入口可能重复发起 Transport disconnect → 原子终态门控与计数测试验证一次有效关闭；幂等调用必须保留首个终态。
- 单会话 panic 可能毒化输出锁，并在 FFI 持有会话表锁时扩散 → 表锁外执行会话操作，锁中毒映射为受损会话的内部故障；以双会话集成测试验证隔离。
- Rust 新增错误和记录字段影响 Swift 穷举映射 → 同一变更更新所有调用方、fake 和绑定，按双端构建门禁验证。
- 有界文件队列或磁盘故障仍可能造成文件缺口 → 内存保留降级信息与计数，不承诺磁盘不可写时仍完整持久化；不得影响 SSH 连接状态。
- 未发生具体退出事件的服务器仍无法给出根因 → 明确标注未知，仅保留真实可得的协议数值，避免根据 Close 编造原因。

## Migration Plan

1. 评审本提案；实施前复核当前源码与重叠变更，保持其他进行中工作的修改。
2. 各模块先提交能证明旧行为不满足要求的失败测试，再实现最小修复和必要重构；任务清单按依赖排列。
3. 同步生成 Swift 绑定，更新 macOS / iPadOS 错误提示与日志窗口，执行 Rust 和 Swift 验证。
4. 升级后新事件使用规范路径，旧日志原样保留；发生回滚时旧程序仍可使用原路径，SSH 主机与凭据配置没有迁移。
5. 验证通过并完成验收后将 delta 合并主规格并归档；当前创建阶段不执行此步骤。

## 验证与验收

**Verification（实现符合规格）**：使用可控 fake 和事件序列验证：满队列被拒后连接存活、已接纳字节顺序一致且无自动重放；正常退出与信号/非零/未知关闭互异；正常退出显示已结束而非失败；关闭竞争只发起一次有效 disconnect；后台任务意外退出无需额外输入即可被发现；单会话锁中毒不影响第二会话；故障在连接释放后仍出现在日志且没有敏感测试标记；倒序 FFI 数据在 UI 中显示最新在底部；持久化失败不递归、不误关、恢复后可继续写。失败标准为任一原因被压平或覆盖、输入被静默丢弃、重复发送、假报正常、重复关闭、跨会话失败扩散、重复写日志或泄漏敏感标记。

**Validation（是否解决用户现象）**：实施后在 macOS 与 iPadOS 验证输入、粘贴、切换日志页、退出和手动重试；对受控 fake 服务器注入传输中断及远端异常退出。用户现场若再次断线，应能关联到该会话、阶段与可得的具体类别；若仍只能得到通用“SSH 通信异常”，诊断目标未达成。真实服务器的网络或远端程序根因需后续证据，不以本地测试代替现场结论。
