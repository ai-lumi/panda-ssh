# SSH 跳板机（Proxy Jump）

> 状态：草案 | 创建日期：2026-09-09 | 关联路线图：brainstorming-ai-era-roadmap.md 5.4、#8、#12

## 问题

路线图 1.4 识别跳板机为当前演进缺口：配置引用之外还需每跳认证、指纹确认、环检测和失败清理。

当前 `SshSession::connect` 直接以 `TcpStream` 连接目标主机的 `(host, port)`，尚无跳板配置字段。用户需要通过中间主机（跳板机）访问内网服务器时，只能手动建立隧道或使用外部工具，无法在应用内完成端到端连接。

路线图 5.4 已决采用方案 A：`HostConfig.proxy_jump` 引用已有 `HostConfig` id。方案 B（内嵌代理配置）保留为已比较替代，不作为当前方向。

需要补齐的设计：
- 每跳独立凭据获取与认证
- 每跳未知指纹确认与密钥变更阻断
- 自引用/环/最大链深检测
- 逐跳与整链超时、取消和部分失败清理
- 配置导入导出中的 ID 重映射与悬空引用
- 被引用跳板机的删除约束（RESTRICT）
- 跳板链变化对已审核任务的影响

## 目标

1. 支持通过一级或多级跳板机建立 SSH 连接，跳板机引用已有 `HostConfig` id。
2. 每跳独立进行主机密钥校验和认证，复用现有 `KnownHosts` 和 `Credentials` 体系。
3. 防止配置环、超深链和悬空引用，在 Rust 配置层统一强制检查。
4. 连接失败时正确清理已建立的中间跳板连接，不泄漏资源。
5. 跳板链变化使已审核的执行计划授权失效，须重新核验。

## 范围

### 包含

- `HostConfig` 新增 `proxy_jump` 可选字段（引用已有 `HostConfig` id）
- 连接流程改造：递归解析跳板链，逐跳建立 SSH 连接，最终通过 `direct-tcpip` 通道承载目标 SSH
- 每跳独立的主机密钥校验（复用现有 `KnownHosts` + `UnknownHostKeyPolicy`）
- 每跳独立的凭据获取（复用现有 `Credentials` + 凭据文件体系）
- 环检测、最大链深限制、悬空引用检测
- 被引用跳板机删除的 RESTRICT 约束
- 失败清理：连接链中任一跳失败时，关闭已建立的中间连接
- 配置导入导出中的 ID 重映射与悬空引用处理
- FFI 绑定更新，支持跳板机配置
- SwiftUI 界面：跳板机选择器、连接时的逐跳指纹确认流程

### 不包含

- 方案 B（内嵌代理配置）——已决不采用
- SOCKS 代理或 HTTP 代理——独立能力，不在本提案范围
- 端口转发/隧道——独立提案
- 跳板机上的命令执行或 SFTP——跳板机仅用于中转

## 验收标准

- [ ] `HostConfig` 支持 `proxy_jump: Option<String>` 字段，序列化为 TOML 后为跳板机 id
- [ ] 单跳代理连接端到端可用（跳板机 → 目标主机）
- [ ] 多级跳板连接可用（A → B → C → 目标），链深不超过上限
- [ ] 每跳独立进行主机密钥校验：Unknown 走 TOFU 流程，Mismatch 阻断
- [ ] 每跳独立认证：密码或密钥，凭据按各自 `HostConfig` 的 `auth` 配置获取
- [ ] 自引用检测：`proxy_jump` 指向自身 id 时拒绝
- [ ] 环检测：A → B → A 等环形引用时拒绝
- [ ] 最大链深限制：超过上限时拒绝（建议上限 8 跳）
- [ ] 悬空引用检测：`proxy_jump` 引用的 id 不存在时拒绝
- [ ] RESTRICT 删除：被引用的跳板机无法删除，须先解除引用
- [ ] 失败清理：中间跳认证失败或超时时，已建立的连接全部关闭
- [ ] 配置导入导出：ID 重映射正确，悬空引用不静默丢弃
- [ ] FFI 绑定覆盖跳板机配置读写
- [ ] `cargo test` 全绿，覆盖率 >= 95%
- [ ] 跳板链变化使已审核计划授权失效（与审计/授权提案联动）

## 风险

- **中风险**：多级跳板的递归连接和失败清理逻辑复杂，需充分测试
- **中风险**：`direct-tcpip` 通道的流式承载需要自定义 `AsyncRead`/`AsyncWrite` 实现，替代 `TcpStream`
- **低风险**：配置层变更（新增字段）向后兼容，旧配置无 `proxy_jump` 时按 `None` 处理
- **依赖**：russh 的 `channel_open_direct_tcpip` 能力已确认（路线图 #2 调研）
