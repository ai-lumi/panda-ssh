### 5. add-ssh-proxy-jump — SSH 跳板机

**优点**：
- **设计深度且完整**：数据模型、连接流程、流抽象、密钥校验、凭据获取、超时策略、失败清理、配置导入导出、安全约束——每个方面都有详细设计
- **复用现有体系**：KnownHosts、Credentials、ConfigStore 全部复用，不重复造轮子
- **校验约束完备**：自引用、环检测、深度限制、悬空引用、删除 RESTRICT——全部覆盖
- **Spec delta 质量高**：新增 proxy-jump/spec.md + 修改 host-config/ssh-connection/host-key-verification 三个现有 spec
- **向后兼容**：`proxy_jump: Option<String>`，旧配置无影响
- **任务拆分合理**：6 阶段 15 任务，依赖关系清晰，预估 23 小时

**问题与建议**：
- **[P1] `direct-tcpip` 通道的 `AsyncRead`/`AsyncWrite` 实现风险**：design 提到需包装 russh Channel，但未验证 russh 的 `Channel<client::Msg>` 是否直接支持这种用法。建议增加一个技术验证任务（spike）。
- **[P1] 中间会话生命周期管理**：design 中 `_proxy_chain: Vec<SshSession>` 字段方案可行但增加 SshSession 复杂度。建议确认 Drop 顺序保证（Rust Drop 顺序为字段声明顺序，需验证反序关闭语义）。
- **[P2] 逐跳指纹确认 UI 流程**：tasks.md 中 T14 描述较简略。多跳时需多次弹出确认框，用户体验需要更细致的设计（如一次展示全部未知密钥）。
- **[P2] 整链超时**：design 决定不引入独立整链超时（各跳超时之和自然构成上限），最坏情况 `8 * 90s = 720s`。这在用户感知上可能偏长，建议在 UI 层提供取消入口。

**评审结论**：方案优秀，设计深度足够。建议增加 russh direct-tcpip 技术验证任务后开始实施。

### 6. improve-connection-reliability — 连接可靠性

**优点**：
- **三阶段设计合理**：会话持久化 → 自动重连 → 端口转发，逐步递进
- **会话持久化方案完备**：代际追踪、过期清理、应用重启恢复
- **自动重连安全约束到位**：退避策略、凭据失效处理、密钥变更阻断
- **端口转发覆盖三种类型**：本地、反向、动态（SOCKS5），并明确安全约束（仅绑定 loopback）
- **任务拆分清晰**：19 个任务，三阶段可并行开发，预估 14 天

**问题与建议**：
- **[P0] 缺少 `.openspec.yaml`**：建议补充。
- **[P1] 自动重连的 russh 限制**：russh 的 `ClientHandler` 在连接断开后是否支持重新握手？需要确认 russh 是否需要在重连时创建全新的 `AsyncClient` 而非复用。
- **[P1] 端口转发与跳板机的交互**：本提案的端口转发是否经跳板链？design 未明确。如果经跳板链，需与 #5 协调。
- **[P2] 会话持久化存储格式**：design 提到 TOML 文件，但未明确敏感信息（如 shell 工作目录）的存储策略。
- **[P2] SOCKS5 实现复杂度**：动态端口转发需要完整的 SOCKS5 协议实现，工作量可能超过预估的 5 天。

**评审结论**：方案方向正确，范围较大建议确认优先级。会话持久化和自动重连优先级高于端口转发，可考虑拆分为独立提案。

### 7. deepen-snippet-system — 代码片段深化

**优点**：
- **多级标签设计合理**：`/` 分隔 + `tags.toml` 索引，兼容现有数据，无需迁移
- **标签树可从 frontmatter 重建**：`tags.toml` 丢失不致命，只丢失颜色/描述
- **搜索语义明确**：多关键词 AND，大小写不敏感，覆盖标题/标签/内容
- **模板引擎简洁**：`{{变量名}}` 语法 + 单引号 shell 转义，不引入外部模板引擎
- **终端选文入口设计简洁**：不涉及 Rust 变更，纯 Swift UI 入口

**问题与建议**：
- **[P1] 标签重命名原子性**：design 承认"逐文件更新，中途失败已更新保持新值"。对于大量片段（如 100+）的重命名操作，失败恢复策略是"再调一次逆操作"——但这可能产生不一致状态（部分已更新部分未更新）。建议考虑引入临时备份文件。
- **[P1] 搜索性能**：当前设计为全量遍历 + `contains` 匹配。片段数量在千级时可能感知到延迟。建议标注性能边界（如 1000 片段 < 100ms）。
- **[P2] 模板引擎缺少 `{{name:default}}` 语法的详细规格**：design 提到支持默认值但 `extract_vars` 实现细节未展开。
- **[P2] 标签颜色在 iPadOS 的展示**：颜色元数据在 iPadOS 小屏幕上可能不太实用，建议标注为 macOS 优先。

**评审结论**：方案通过，设计合理。标签重命名原子性是需要关注的风险点。

### 11. add-manual-inspection-loop — 人工巡检闭环

**优点**：
- **测量契约优先**：先定义指标与失效边界，再定义采集和闭环——这是本提案最大的亮点
- **质量状态语义严格**：有效/不可用/不支持/采集失败/过期，缺失不得记为零或正常
- **逐指标定义详尽**：5 个首批指标（CPU 利用率、负载/核、内存使用率、文件系统容量、失败服务）每个都有完整的测量方法、失效边界和入选理由
- **三分离设计**：方案、计划、执行记录互不干扰
- **内容寻址版本化**：方案版本 = SHA-256 内容哈希，保证不可变性
- **SQLite 容量估算**：不凭"数十万条无压力"断言，而是基于实际参数估算（~100-400 MB/年）
- **HTML 导出安全设计**：远端文本按不可信数据处理，单文件离线，上下文正确转义
- **Spec 质量极高**：四个 spec 文件覆盖了方案管理、测量契约、执行闭环和报告展示

**问题与建议**：
- **[P0] 依赖三个并行提案**：#8（批量执行）、#9（授权）、#10（审计）均未合并。runner 集成任务（第 8 组）被阻塞。建议确保 `InspectionExecutor` trait 抽象足够稳定，使集成任务可在最后对接。
- **[P1] rusqlite bundled 的 iOS 静态链接**：design 提到风险但无 fallback 验证结果。建议将 iOS 静态链接验证作为第一个技术验证任务。
- **[P1] 首批指标全部面向 Linux**：5 个指标全部依赖 `/proc` 和 `systemctl`，macOS 目标主机全部"不支持"。建议明确标注首批指标仅支持 Linux 目标，并在 UI 中如实展示。
- **[P2] 默认阈值未经验证**：design 诚实标注"草案，未经行业基准验证"。建议在巡检 UI 首版中默认引导用户审核阈值而非直接使用默认值。

**评审结论**：方案极其详尽，是所有提案中设计质量最高的。测量契约优先的理念值得肯定。关键风险在于依赖链和 iOS 平台验证。

- 九态状态机的枚举定义与流转规则

## 五、总结

### 整体评价

这批提案的**整体质量很高**，体现了以下特点：

1. **问题驱动**：每个提案都从明确的问题出发，而非技术驱动
2. **架构一致**：所有业务逻辑落 Rust、Swift 仅 UI、FFI 同步导出——一致性极好

5. **TDD 执行扎实**：Phase 0 的测试补齐覆盖了 200+ 用例

2. **迁移长尾**：`SftpSessionStore` 选择逻辑、`ConnectionGate` 状态机等硬骨头未啃
3. **iOS 平台验证**：rusqlite bundled 静态链接、端口转发后台限制等需真机验证
4. **工作量过大**：12 个提案 60+ 天工作量，需要明确里程碑和优先级
