## 五、功能提案深度分析

> #14 修订：保留功能方向与既有用户决策，修正依赖和低估的风险。本章是提案输入，不能替代正式 OpenSpec 设计或授权。

### 5.0 依赖关系总览

```
现有片段 CRUD + 终端选文 → 片段深化（不依赖完整操作历史）
现有 SSH exec + 授权/任务状态/审计 → 手动批量执行 → 巡检闭环
                                          ↑
命令历史的可核对命令 ──→ 后续复用入口（重新审核，不继承授权）
跳板机 ──→ 需要内网访问的任务（其他任务可先用直连主机）
已审核且成功验证的巡检计划 → 用户启用 macOS 定时巡检
```

授权、失败语义、资源限制和审计是受控执行的共同前置；原始终端录像、向量搜索、完整记忆与拓扑不是批量执行或 AI 增益实验的硬前置。

### 5.1 提案 1：本地命令历史与审计

**目标：** 本地命令执行历史作为审计记录，关联目标、会话/任务、操作者或调用主体、计划/授权、时间、命令、执行结果和验证证据；删除后能够清楚发现历史缺段。具体格式和存储方式在审计提案中详细设计。

**记录渠道与证据边界：**

| 渠道 | 可以记录的事实 | 限制 |
|------|----------------|------|
| 应用代发的 exec/批量/巡检 | 实际提交的命令、确定的目标、批准版本、结果状态 | 超时或断线不证明远端未执行；缺少退出状态时不能填零 |
| 手动交互 shell | 明确捕获到的命令边界、会话事件及其来源 | 原始按键受行编辑、TUI、嵌套 shell 影响，不能当作完整命令清单 |
| SFTP | 路径/目标、操作类别、冲突决策、终态等审计元数据 | 不默认记录文件正文，凭据与敏感内容须过滤 |
| 可选终端录像 | 已授权范围内的输出、尺寸变化、时间线 | 录像不能替代结构化审计；输出也可能含秘密 |

**命令边界：** 客户端代发命令可准确知道提交内容；交互命令优先利用 shell integration 协议信号，正则与手工标注仅补充。信号来自远端，不能作为可信身份或授权来源；不可辨识区域明确标记「命令覆盖未知」。嵌套 SSH 不凭一段文本自动更改主机身份或授予新目标权限。

SwiftTerm 提供界面选择和终端事件，审计规则、持久化和校验逻辑在 Rust；不把 Swift 的输入拦截点变成仅能记录 GUI 操作的业务实现。MCP 与调度入口也必须覆盖。

**连续性与删除：** 支持查看缺段的范围及可知原因，区分授权清理、异常缺失、证据不足和不可验证；合法删除不抹去清理留痕。学习系统只能消费允许的派生视图，不改写原记录或完整性结论。记录编号、完整性证明、删除留痕、轮转、备份恢复、崩溃修复与密钥管理，均留到提案设计。

**隐私与可信边界：** 不默认记录逐键输入；秘密不得进入一般审计内容。必要脱敏有明确标记，并保留非敏感关联元数据。须说明仅本地证据对整库替换、尾部截断与旧备份回滚的检测边界，不能宣称完整抵御本机管理员篡改；也不能因可被删除而取消审计定位。

| 阶段 | 内容 | 验收重点 |
|------|------|----------|
| 首个执行闭环 | 应用代发命令与 SFTP 审计、连续性检查、删除缺段展示 | 正常链路、失败/未知、缺段、篡改与写入中断；格式由提案决定 |
| 交互记录深化 | shell integration 与低置信标注 | 行编辑、多行命令、TUI、嵌套 SSH、伪造标记均不误报完整覆盖 |
| 按需求扩展 | 可选录像与回放 | 授权、脱敏、尺寸变化、资源限制与删除关联；不能阻塞最小巡检闭环 |

### 5.2 提案 2：代码片段深化

**已有基础：** Rust `Snippet`/`SnippetStore`、FFI 与真实 Swift 后端已经有列表/保存/删除实现；Swift `SnippetsView` 有编辑、复制等入口。应逐项验收与深化，不能重新列为全新能力。

| 能力 | 依赖与边界 |
|------|------------|
| 终端选文 → 片段 | 终端选择 API 与片段 CRUD 即可；不依赖操作历史 |
| 多级标签与搜索 | 复用现有 tags；处理旧数据与查询边界，见 5.7 |
| 编辑器体验 | 按用户反馈增加，不先建设完整 IDE |
| 参数化模板 | 先明确参数类型、引用与 shell 转义；不依赖完整历史，执行时仍重新审核 |
| 片段 → 批量任务 | 将具体片段版本展开进执行计划；保存的片段不是自动获批的命令 |

片段名称/ID、Markdown 正文与 Swift 展示字段需确定稳定映射。已审核任务固定引用内容，片段更新不能静默改变已授权计划；与巡检的引用关系见 8.7。

### 5.3 提案 3：远程命令批量执行

**已有原语：** `SshSession::exec` / `exec_with_timeout` 可非交互执行，收集 stdout/stderr 和可选退出码；默认等待超时为 60 秒。它是执行原语，不是完整任务引擎。

**必须补齐的契约：**

| 领域 | 要求 |
|------|------|
| 目标与审批 | 多选/分组解析成明确目标集合，展开参数后审核；AI 与历史选择不继承权限 |
| 执行状态 | 区分排队、等待批准、运行、成功、失败、超时、取消请求、已确认停止、结果未知 |
| 超时与取消 | 停止等待不等于远端已停止；未知结果保持可见，重连不自动重发 |
| 有界资源 | 主机并发、每主机步骤并发、输出大小、等待时间、总预算及背压策略 |
| 结果与恢复 | 逐主机终态、部分成功、崩溃恢复、重入核对；未收到退出码不得默认成功 |
| 重试与补偿 | 仅按明确的可重试条件与预算重试；任意 shell 命令不承诺恰好一次或通用回滚 |
| 业务验证 | 执行成功与目标完成分别判断；健康检查、版本核对等验证步骤也在计划中审核 |
| 连接所有权 | 任务拥有其 Transport 与句柄；不从终端标签隐式借用连接，关闭不影响其他所有者 |
| 审计 | 关联计划、批准、尝试和结果；连续性校验及缺段展示纳入同一闭环 |

**实施顺序：** 先用 fake SSH/时钟/存储测试正常、错误和边界行为；再实现手动输入、多选、有限并行与结果持久化；之后增加片段/历史入口、灰度批次与条件步骤。计划预览是审批前置，不延后到远期。

验收必须包含「远端已经执行、回包前断线」以及「用户撤销后尚有步骤排队」，确保不会盲目重试、误报成功或继续扩大执行。

### 5.4 提案 4：SSH 跳板机（Proxy Jump）

[已决] 采用方案 A：`HostConfig.proxy_jump` 引用已有主机 ID。方案 B（内嵌代理配置）保留为已比较替代：配置自包含，但需要额外凭据约定和嵌套模型；不作为当前方向。

```toml
# 候选字段；最终契约在 OpenSpec 提案中确定
proxy_jump = "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"
```

[已核对] 当前连接走 `connect_stream`，`CountingStream` 的底层为 TcpStream，尚无跳板配置。技术候选为 direct-tcpip 通道转为流后承载目标 SSH；不能把整个功能估计成仅替换流类型。

**设计必须覆盖：** 每跳独立凭据获取、未知指纹确认与变更阻断；自引用/环/最大链深；逐跳与整链超时、取消和部分失败清理；DNS 与目标身份归属；完整路径的审计和授权；连接及父链生命周期；配置导入导出中的 ID 重映射与悬空引用。

[建议] 删除被引用跳板机采用 RESTRICT，显示引用方并提供显式替换操作（14.9）。约束在 Rust 配置层统一实现，不能仅靠 UI 禁用按钮；导入和 MCP 入口也需遵循。

跳板链变化影响已经审核的任务，须按第四、十三章重新核验或失效，不能悄悄改走直连。

### 5.5 优先级建议

| 优先顺序 | 工作 | 说明 |
|----------|------|------|
| 基线关卡 | 统一凭据/连接/片段现状，定义授权与审计边界 | 避免基于冲突规格继续叠加功能 |
| 已决基础方向 | 跳板机、片段深化 | 保留既有优先方向；按实际试点的访问与复用需求安排 |
| 首个纵向闭环 | 手动批量执行 + 可发现缺段的审计 + 小范围巡检 | 可独立验证价值，不等所有基础功能完成 |
| 有条件扩展 | macOS 定时巡检、受控 MCP、薄 AI 辅助 | 先通过人工审核/执行验证及 8.5 的关卡 |
| 需求或增益证明后 | 录像、命令解析深化、向量、拓扑、复杂编排 | 不作为所有后续能力的默认前置 |

### 5.7 多级标签系统调研（代码片段分类）

[已决] 一个片段可有多个层级标签；使用 `/` 分隔路径；默认 OR，可切换 AND；frontmatter 保存路径字符串，`tags.toml` 保存索引。

```yaml
tags: ["网络/内核参数", "故障处理/生产事故", "性能优化/延迟调优"]
```

需补齐的设计边界：

- 旧标签可能本来含 `/`，需要明确迁移/转义规则，不能无条件称「零迁移成本」。
- 子树查询必须满足 `tag == prefix` 或 `tag.starts_with(prefix + "/")`，避免父标签漏匹配及同名前缀误匹配。
- 若 `tags.toml` 只存派生树，丢失可以重建；若还存颜色、描述、空标签等独立元数据，则必须有独立保存/恢复策略，不能同时宣称全部可重建。
- 父标签重命名涉及多个 Markdown 文件，需定义失败恢复与索引一致性；标签删除不删除片段正文。
- 路径规范化、空层级、重复标签、最大层级和 OR/AND 的空选择语义，纳入正常/异常/边界用例。
- 片段标签不能直接当作主机标签。主机多维选择仍需单独数据模型，并在审批时冻结最终主机集合。

UI 保留树形浏览、自动补全和标签管理方向；查询与变更规则统一在 Rust 核心。
